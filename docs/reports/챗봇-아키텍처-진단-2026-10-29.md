## 2) 문제점 목록

각 항목: 위치 · 원인 · 발생 조건 · 사용자 영향. 우선순위는 4)에서 다시 정리한다.

### F1. 답에 쓴 수치가 실제 집계와 일치하는지 검증하지 않는다 — P0
- 위치: `AgentService.answer()`(239–269), `answer.py _answer_from()`(241–257), `RagService.view()`(335)
- 원인: 서버는 인용 번호([n])와 출처 존재만 확인한다. summary·points·body 문장 안의 "5건", "+200%", "유행점수 3" 같은 숫자는 Claude가 도구 결과를 읽고 다시 쓴 자유 텍스트다. [확인]
- 발생 조건: 숫자를 쓰는 질문(증감·비교·표·브리프). 특히 도구를 여러 번 부른 비교 답에서 값을 옮기다 섞이기 쉽다. [추정]
- 영향: 화면의 판단 근거 막대(서버 값)와 답 본문 숫자가 다를 수 있고, 사용자가 이를 구분할 방법이 없다. 사후 점검도 어렵다(F4).

### F2. 지어낸 인용 번호를 지우면 그 줄이 "근거 없는 문장"으로 남는다 — P0
- 위치: `AgentService.answer()` 247행(목록 밖 번호 제거), `answer.py` 248·251행, `RagService.points()` 405–421행
- 원인: AI 서비스·AgentService가 존재하지 않는 번호를 먼저 지운다. 그다음 Spring `points()`는 "처음부터 인용이 없는 줄 = 한계·주의 문장"으로 보고 남긴다. 둘을 구분할 정보가 사라진다. body도 같다(번호만 지우고 문장은 남김). [확인]
- 발생 조건: 모델이 [7]처럼 없는 번호를 인용했을 때.
- 영향: 근거 없는 사실 주장이 출처 표시 없이 답에 남는다. 규칙("근거 없는 줄은 한계 문장뿐")과 반대로 동작한다.

### C1. "매체 수"와 "유행점수의 출처"가 서로 다른 기준이다 — P0
- 위치: `TrendFactsService.countIn()` 299·312행(`doc.getMedia()`), 379행(질문 단어), `sourceKey()` 106행
- 원인: 유행점수는 `sourceKey`(직접 업로드·매체 미입력은 원문마다 다른 출처)를 쓰지만, 매체 수는 매체명 원문 그대로 센다. 이미지 업로드 원문은 모두 "직접 업로드" 한 곳이 되고, 매체가 null이면 null도 한 곳으로 센다. [확인]
- 발생 조건: 이미지 업로드 위주인 범위(현재 데이터 대부분). [추정]
- 영향: 같은 값이 "유행점수 6"이면서 "매체 1곳"으로 나온다. 화면은 "· 1개 매체"를 붙이고(home.html 1041), 프롬프트 규칙("매체가 한 곳뿐이면 대중화 여부는 더 봐야 한다")이 잘못된 유보 문구를 만든다. 판단 근거와 답이 서로 모순된다.

### B1. 판단 근거 상자가 답과 다른 범위를 보여줄 수 있다 — P0
- 위치: `AgentService.countText()` 176행(`firstFacts`는 첫 집계), `run()`의 prefetched, `RagService.agentView()` 160행
- 원인: 판단 근거 상자는 항상 첫 집계, 즉 해석 범위로 미리 센 prefetched다. Claude가 다른 범위·기간으로 count_trend를 다시 불러 답해도 상자는 바뀌지 않는다. [확인]
- 재현: "레더 재킷과 무스탕 중 어떤 아이템이 더 유행해?" → 해석은 대상이 둘이라 범위를 비우고 terms만 남긴다(interpret.md 36행). prefetched는 "전체" 집계가 되고, Claude는 대상별로 다시 센 값으로 답한다. 상자는 "전체 · 아이템 종류 막대"를 보여준다. [추정]
- 영향: 답(레더 vs 무스탕)과 아래 막대(전체 아이템 순위)가 달라 신뢰를 떨어뜨린다.

### B2. 도구 경로에 문서 검색 도구가 없어 "이유·설명" 질문을 근거로 답할 수 없다 — P1
- 위치: `agent.py` TOOLS(35–58), `interpret.md` trend 기준(18행)
- 원인: 해석은 특징·경향·추천·정리까지 모두 trend=true로 보낸다(사용자 결정). 도구 경로에서 쓸 수 있는 원문 정보는 예시 원문 요약 160자(`AgentService.SUMMARY_CHARS`)뿐이고, Chroma 본문 청크 검색 도구는 없다. [확인]
- 재현: "와이드 팬츠가 유행하는 이유는?" → trend=true(경향) → 숫자와 짧은 요약만 받음 → 상식으로 채우거나(규칙 위반) grounded=false로 끝남. [추정]
- 영향: 원인·배경·맥락 질문의 대응 범위가 비어 있다. "집계 + 문서 근거" 복합 질문(예: 브리프의 근거 문장)도 같은 한계를 가진다.

### B3. 추이 도구가 "최근 3개월"과 여러 값 비교를 감당하지 못한다 — P1
- 위치: `AgentService.trendSeries()` 190–211행(`MAX_SERIES_WEEKS=12`, 값 하나), `TrendFactsService.series()` 566행
- 원인: 최대 12주(84일)이고 한 번에 값 하나만 센다. 도구 호출 상한은 6번이다. [확인]
- 재현: "최근 3개월간 아우터 트렌드가 어떻게 변했어?" → 3개월(약 13주)을 다 덮지 못한다. 상위 5개 종류의 추이를 보려면 series 5번 + count 1번으로 상한에 닿는다. 마지막 주(진행 중)도 같은 막대로 나온다. [추정]
- 영향: 추이 답이 일부 기간이나 일부 값만 보고 결론을 낸다.

### C2. 수집량 변화를 보정하지 않는다 — P1
- 위치: `TrendFactsService.rate()` 85행, `rank()` 419행(증감 정렬 = 원문 수 차이)
- 원인: 증감률과 증감 정렬은 원문 수 절대값으로 계산한다. 범위 전체 원문 수(`prevDocCount`)는 있지만 점유율(값 원문 수 ÷ 범위 원문 수)로 비교하지 않는다. [확인]
- 재현: 이번 4주에 이미지를 60건 일괄 업로드했고 직전 4주가 10건이면, 거의 모든 값이 "+수백%"가 되어 "급상승"으로 나온다. [추정]
- 영향: 증감·급상승 답이 유행 변화가 아니라 수집량 변화를 보여준다.

### C3. 작은 표본의 증감을 그대로 순위에 올린다 — P1
- 위치: `rank()` UP 필터(`delta > 0`), `rate()`(0→1 "신규")
- 원인: 최소 건수 기준이 없다. 답변 규칙의 "유행점수 2 이상만 핵심"은 증감 정렬에는 적용되지 않는다. [확인]
- 영향: 0→1, 1→2(+100%) 같은 값이 "급상승 아이템"으로 답에 나올 수 있다.

### C4. 라인(성별) 조건은 라인 값이 없는 예전 결과를 조용히 뺀다 — P1
- 위치: `Scope.matches()` 252행(필터 값이 없으면 불일치), rag-search.md 27행
- 원인: GENDER 값은 최근 분석부터 생겼다. "남성 아우터"는 라인 값이 있는 옷만 센다. [확인]
- 영향: 표본이 실제보다 작은데 답과 화면 어디에도 "라인 정보가 있는 N건 중"이라는 커버리지가 보이지 않는다.

### C5. 출처 유형(매체·일반 게시물·뉴스)을 구분하지 않는다 — P1(데이터 생기면)
- 위치: `SourceDocument`(매체명 문자열만), `sourceKey()`
- 원인: 출처 유형 칸이 없다. 이미지 업로드는 인스타 게시물로 "간주"할 뿐이다. [확인]
- 영향: 지금은 수기 데이터라 영향이 작다. 수집(P-01)이 붙으면 매체 기사와 일반 게시물의 신호 세기를 구분할 수 없다.

### E1. 차트 출력이 없다 — P1
- 위치: `answer.build_schema()`(summary·points·body·grounded), `home.html renderBody`
- 원인: 답 형식에 차트 칸이 없다. 표는 body의 마크다운으로만 가능하다. 차트 부품(`line-chart.js`, rank-bars)은 있지만 챗봇에서 쓰지 않는다. [확인]
- 영향: "표와 차트로 비교해줘"에는 표만 나온다. 추이 질문도 글로만 답한다.

### E2. 표의 숫자도 Claude가 다시 쓴 텍스트다 — P1 (F1과 연결)
- 위치: answer.md system_trend 43–45행(body 표), `renderBody`
- 원인: 비교표·브리프는 Claude가 마크다운으로 직접 쓴다. 서버 데이터로 채우는 표 컴포넌트가 없다. [확인]
- 영향: 표가 커질수록 옮기다 틀린 값이 섞일 위험이 커진다(F1).

### D1. 기준 유사도 0.60의 측정 근거가 오래됐다 — P1(측정 먼저)
- 위치: `RagService` 생성자 주석(75–77행: 2026-10-21 이미지 32건으로 측정), `rag.min-score`
- 사실: Chroma 컬렉션은 처음부터 `hnsw space=cosine`이고(`vector_store.py` 41행, 커밋 96f9527), 유사도 = 1 − 코사인 거리로 계산한다. **거리와 유사도를 혼동하지 않는다.** [확인]
- 문제: 텍스트 원문과 본문 청크가 들어온 뒤의 분포로 다시 재지 않았다. rag-search.md의 재측정 조건(50건 이상 증가, 텍스트 유입)에 이미 해당할 가능성이 있다. [추정]
- 영향: 근거 없음이 잦아지거나 엉뚱한 근거가 걸릴 수 있다. **값을 바꾸지 말고 `search_eval.py`로 먼저 잴 것.**

### D2. 최신성 가중치가 관련도를 크게 뒤집을 수 있다 — P2
- 위치: `answer.py rank_by_recency()`(유사도 × 0.5^(경과일/28))
- 원인: 8주 지난 근거는 가중치가 0.25다. 유사도 0.80인 8주 전 문서(0.20)가 0.61인 오늘 문서(0.61)보다 뒤로 밀린다. 기준 유사도(0.60)를 넘은 것끼리라 엉뚱한 근거는 아니다. [확인]
- 영향: "부츠컷이 뭐야?", "레더 재킷 코디 보여줘"처럼 시점과 무관한 질문에서 가장 잘 맞는 자료가 top 8 밖으로 밀릴 수 있다.

### D3. 질의 확장이 없다 — P2
- 위치: `answer.search()`(질문 1개 임베딩)
- 영향: 표기가 다른 질문(스웨이드/suede, 바람막이/윈드브레이커)의 재현율은 임베딩 모델 성능에만 의존한다. 요약 청크가 한국어 코드 이름으로 쓰여 일부는 보완된다. [추정]

### F3. 판단 근거와 AI 해석이 한 화면에서 구분되지 않는 경우가 있다 — P1
- 위치: home.html `renderAnswer`
- 사실: 판단 근거 상자(서버 값)와 답 본문(Claude 해석)은 분리돼 있다. 하지만 B1(범위 불일치)과 F1(수치 미검증) 때문에 사용자가 "서버가 센 숫자"와 "AI가 쓴 숫자"를 구분할 수 없다. [확인]

### F4. 질문 로그에 도구 호출과 집계 스냅샷이 없다 — P2
- 위치: `RagLogService.record()`, `AgentService.Result.calls`(만들어지지만 저장 안 됨)
- 영향: 👎 받은 답의 숫자가 맞았는지 사후에 확인할 수 없다.

### P1-비용. 도구 경로가 실패하면 토큰이 로그에서 빠지고 비용이 두 번 든다 — P2
- 위치: `RagService.ask()` 149–156행(성공 때만 `meter.add`), `AgentService.run()`
- 원인: 실패한 도구 경로의 토큰은 버리고 고정 경로를 다시 호출한다. 시간 상한(90초)은 단계 사이에만 확인한다. 한 단계 응답은 HTTP 읽기 제한 3분까지 기다린다(`AiClient` 40행). [확인]
- 영향: 질문 로그의 평균 토큰이 실제보다 적다. 최악의 경우 응답이 90초를 훨씬 넘는다.

### P2-성능. 집계가 질문마다 메모리에서 전체를 센다 — P2
- 위치: `countIn()`(기간 원문 전부 로드), `latestDate()`(DONE 원문 전부 로드)
- 사실: 1초를 넘으면 경고 로그를 남기도록 이미 대비돼 있다. 지금 데이터 규모에서는 문제가 아니다. [확인]

### 확인했으나 문제가 아닌 것
- 같은 원문 이중 집계: 원문 단위 Set으로 세고(한 원문에 여러 번 나와도 1), 저장 단계에서 URL과 이미지 해시로 중복을 막는다. [확인]
- 현재 기간과 직전 기간 비교: 같은 길이, 같은 범위·시즌·필터로 센다(`countIn`). [확인]
- 직전 0건 증가율: "신규"로 표시하고 나누지 않는다. [확인]
- 데이터 부족과 오래된 자료 안내: stale(8주), "가장 최근 자료 4주", 단일 매체 문구가 있다. 단, C1 때문에 단일 매체 문구는 잘못 붙을 수 있다. [확인]
- 이미지·텍스트 통합: 원문 1건 = 본문 + 이미지를 한 번에 정형화하고, 집계는 원문 단위다. [확인]
- 사용하지 않은 출처 표시: 출처 목록은 인용된 번호만이다. [확인]
- 출처 ID 연결: doc_id로 RDB 원문을 다시 읽고 DONE만 남긴다. [확인]
- 도구 입력 검증: 공통코드 밖 값과 잘못된 기간은 "입력 오류"로 되돌려 다시 부르게 한다. [확인]
- 단순 질문의 AI 호출 수: 해석 1회 + 도구 경로 1회(prefetched로 바로 final_answer)로 대개 2회다. [확인]

## 3) 개선안

원칙: 지금 구조(해석 → 도구 경로/검색 → 출처 검증)는 유지한다. **숫자와 출처는 서버가 만들고, Claude는 무엇을 셀지와 해석 문장을 맡는다**는 현재 원칙을 끝까지 적용한다.

### 개선 전후 구조

```
[전] Claude ─ final_answer(summary · points · body: 숫자·표 모두 텍스트) ─▶ 서버: [n]만 정리
[후] Claude ─ final_answer(summary · points · body + data_refs/chart 지정) ─▶ 서버:
        · [n] 정리 + 지어낸 번호가 있던 줄 표시/제거 (F2)
        · 본문 숫자 ↔ 이번 실행의 도구 결과 숫자 대조, 불일치 로그·경고 (F1)
        · 표·차트는 서버가 도구 결과로 채운 컴포넌트 (E1·E2)
        · 판단 근거 = 답이 실제로 쓴 집계 (B1)
     도구: count_trend · trend_series(여러 값·최대 26주) · search_documents(신규) · final_answer
```

### 해석 필드 확장에 대한 판단 (A)

과제가 제시한 `intent / comparison_targets / output_format / analysis_requirements`는 **지금은 추가하지 않는 것을 권한다.**
- 경로 분기에 쓰는 것은 `fashion`, `trend` 두 개뿐이다. 유행 질문의 세부 판단(비교·추이·제외)은 2026-10-29 결정대로 Agent가 한다. 해석에 칸을 늘리면 Haiku 해석과 Agent 판단이 두 군데에서 어긋날 수 있다.
- `output_format`은 프롬프트 규칙(표·문단·N줄 → body)으로 이미 처리한다. 차트만 스키마가 필요하고(E1), 이것은 해석이 아니라 final_answer 칸이다.
- `comparison_targets`는 terms(대상마다 질문 단어)로 넘기고 Agent가 대상별로 센다. 이 부분은 B1(근거 상자)을 고치면 충분하다.
- 예외: B2(검색 도구)를 넣은 뒤에도 "이유" 질문이 검색을 안 부르면, 그때 해석에 `needs_text_evidence` 같은 불리언 하나만 추가해 prefetched와 함께 검색 결과도 미리 넣는 방안을 검토한다.

| T5 | 최근 3개월간 아우터 트렌드가 어떻게 변했어? | 13주 추이 또는 월별 count 3회 | 3개월 아우터 원문 | 기간이 3개월 전체를 덮음. 진행 중인 주 표시 | **12주 상한(B3)** |
| T6 | 26FW 기획 브리프 만들어줘. | seasons[FALL,WINTER], 모든 축 → body 표 | F/W 시즌 원문 | 표의 숫자 = 집계. 핵심 = 유행점수 2 이상 | 표 숫자 검증 없음(F1·E2) |
| T7 | 유행하는 아이템을 표와 차트로 비교해줘. | body 표 + 막대 차트(서버 값) | 최근 4주 원문 | 차트 값 = facts | **차트 없음(E1)** |
| T8 | 지난달 대비 급상승한 아이템은? | change UP, 최소 표본 적용 | 8주 원문 | 0→1·1→2 값은 "사례"로 분리(C3) | 소표본도 상위에 나옴 |
| T9 | (직전 4주 10건 → 이번 4주 60건 업로드 상태) 요즘 늘어난 컬러는? | 점유율 기준 증감과 수집량 주의 | 수집량 차이가 큰 데이터셋 | 수집량 변화 문구, 점유율 변화(C2) | 거의 모든 값이 급상승 |
| T10 | (이미지 업로드만 있는 범위) 요즘 유행하는 패딩 색은? | 매체 수 = 출처 수 기준 | 이미지 원문만 | "1개 매체" 유보 문구가 나오지 않아야 함(C1) | **잘못된 유보 문구** |
| T11 | 부츠컷이 뭐야? | 검색 경로, 정의 | 부츠컷 언급 원문 | 근거 원문 인용, 유사도 ≥ 기준 | 동작. 최신성으로 좋은 근거가 밀릴 수 있음(D2) |
| T12 | 와이드 팬츠 코디 사례 보여줘 | 검색 경로, 사례 소개 | 와이드 팬츠 원문 | 경향 일반화 없음, 사례마다 인용 | 동작 |
| T13 | 요즘 유행하는 밈은? | OFF_TOPIC | 없음 | AI 해석 1회만 | 동작 |
| T14 | 요즘 유행하는 운동화는? | trend=false → 검색 → 근거 없음 | 없음 | 옷 집계로 답하지 않음 | 동작(해석 AI 성공 시) |
| T15 | 요즘 유행하는 아우터는? → 그럼 하의는? → 지난달은? | 이어 묻기로 다시 쓴 질문 | 2개월 원문 | resolvedQuestion, 기간 라벨 | 동작 |
| T16 | (Claude가 없는 번호 [9]를 인용하도록 모킹) | 그 줄 제거 또는 출처 없음 표시 | 테스트 더블 | 인용 없는 사실 줄이 남지 않음(F2) | **줄이 출처 없이 남음** |
| T17 | (도구 경로 단계에서 AI 오류 모킹) | 고정 경로로 답, 토큰 합산 | 테스트 더블 | 로그 토큰 = 두 경로 합 | 실패 토큰 누락 |
| T18 | 요즘 여성 아우터는 어떤 핏이 많아? | genders[WOMEN] + focus SILHOUETTE | 라인 값 있는 원문 | 첫 축 실루엣, 커버리지 표시 | 커버리지 표시 없음 |
| T19 | 패딩 제외하고 요즘 유행하는 아우터 3개만 | prefetched top 10에서 패딩만 빼고 다음 순위 | 최근 4주 아우터 | 추가 도구 호출 0회, 순서 유지 | 동작 |
| T20 | 올해 F/W랑 작년 F/W 컬러를 비교해줘 | count_trend 2회(기간만 다르게), 표 | 작년·올해 F/W | 같은 조건 비교, 판단 근거 일치 | 근거 상자는 첫 집계만(B1) |
| T21 | 기획 물량: 데님 팬츠 계속 가져가도 될까? | 집계 기반, 결정 단정 금지 | 데님 팬츠 원문 | "참고로만" 표현, 판매 자료 아님 명시 | 동작 |

자동화 제안: T16·T17·T10·T9는 Claude 호출 없이 단위 테스트로 만들 수 있다(`RagTrendApiTest`·`TrendFactsSeasonTest` 방식). T1~T7·T20은 `rag_questions.json`에 추가한다. T3·T4·T5·T7은 지금 평가 세트에 없다.

## 6) 최종 권고안

### 유지할 부분
- 해석 → 도구 경로/검색 두 갈래, OFF_TOPIC 차단, 이어 묻기
- "숫자는 집계 코드가 센다" 원칙, 유행점수, 직전 동일 기간 비교, stale 처리
- prefetched로 단순 질문을 호출 2회에 끝내는 구조, 도구 호출 상한과 실패 시 고정 경로
- 근거 없으면 Claude 미호출, 출처는 RDB 원문으로 되돌림, 인용된 출처만 표시
- 해석 필드는 늘리지 않음(위 A 판단)

### 수정할 부분 (작은 변경)
- F2 인용 정리 로직, C1 매체 수 기준, B1 판단 근거 범위, 실패 토큰 집계, C3 소표본 기준, C4 커버리지

### 추가 개발이 필요한 부분
- B2 `search_documents` 도구, B3 추이 도구 확장, E1 서버가 채우는 차트, F1 수치 대조기(→ 장기적으로 data_refs), C2 점유율, F4 로그 확장, C5 출처 유형(수집 때)

### 단계별 구현 계획

| 단계 | 내용 | 확인 방법 |
| --- | --- | --- |
| 0. 측정 | `search_eval.py`로 기준 유사도 분포 재측정, `facts_check.py` 실행, 현재 답변 평가 기준선(rag_questions + T1~T21) 저장 | 결과를 `ai/evals/results/`에 보관 |
| 1. 신뢰성(P0) | F2 → C1 → B1 → F1①(대조기, 경고만) + 비용 집계 | 단위 테스트(T10·T16·T17), 평가 세트 전후 비교 |
| 2. 대응 범위(P1-a) | B2 검색 도구 → B3 추이 확장 → C3·C4 | T3·T4·T5·T18 |
| 3. 표현(P1-b) | E1 차트(서버 값) → C2 점유율 | T7·T9 |
| 4. 운영(P2) | F4 로그 확장, D2 최신성 완화(측정 후), 집계 성능은 경고 로그가 뜰 때 | 질문 로그 👎 사례 점검 |

각 단계가 끝날 때마다 해당 기능 문서(`docs/llm/features/rag-search.md`)와 평가 세트를 같이 고친다.
