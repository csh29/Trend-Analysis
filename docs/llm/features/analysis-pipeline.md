# analysis-pipeline.md — AI 분석 (P-03 정형화 · P-04 저장·색인)

원문 한 건을 Claude로 정형화(의류 아이템별 카테고리·종류·소재·컬러·실루엣·대상 + 문서 단위 키워드·시즌·요약)하고, 검증해 RDB에 저장한 뒤 Chroma에 색인한다. Spring과 AI 서비스(`ai/`)에 걸친 기능이다.
코드: `service/analysis`(`AnalysisService` 흐름, `TrendResultValidator` 검증, `AiClient` 호출), `ai/app/structuring/structurer.py`·`ai/app/indexing/`(`indexer`·`embedding`·`vector_store.py`). 실행·설정은 [`ai-development.md`](../ai/ai-development.md).
Claude에게 보내는 판단 문구는 `ai/prompts/structure/*.md`에만 둔다. 이 문서에는 결정과 이유만 쓴다.

## 결정 사항 (사용자)

- AI 처리는 Python **FastAPI 서버**로 띄우고 Spring이 호출한다.
- 정형화 LLM은 `claude-sonnet-5-5`(설정 `claude.structure-model`, 챗봇 답변의 `claude.model`과 따로 — 2026-10-29 사용자 결정: 정형화만 먼저 바꾼다). Sonnet 5와 가격·토크나이저가 같고, 정답셋 2장 비교에서 종류 판별이 더 나았다(73장 비교는 아직). 키는 Spring `claude.api.key` **한 곳**에만 둔다.
  - 정형화 모델을 바꾸면 프롬프트 캐시가 새로 시작되고(모델별), 바꾸기 전 결과와 섞여 집계된다(재분석은 필요 없다). 비교는 `ai/evals/structure_eval.py`(모델은 파일의 `MODEL`).
- 표준 코드(카테고리·소재·컬러·실루엣)는 일반 분류 **초안**이다. 확정 체계는 미정(정의서 미결 4번).
- **정형 결과는 의류 아이템 배열**(`items: [{category, item, type, materials, colors, silhouettes, genders}]`)이다. 정의서 10번 형식(문서당 category 1개)에서 벗어난다 — 코디 사진은 아이템이 여럿이라 한 묶음으로 받으면 속성이 섞인다.
- **아이템 종류(`type`, 공통코드 `TREND_ITEM`)**를 아이템마다 고른다. 아이템명(Claude 자유 문장)은 같은 옷도 "데님 트러커 재킷"·"트러커 재킷"으로 갈라져 셀 수 없으므로, 정한 목록(카테고리마다 기타 포함)에서 고르게 한다. 코드값은 `카테고리_종류`(OUTER_PADDING)이고, 아이템 카테고리와 어긋나면 검증이 **종류의 카테고리로 맞춘다**(재시도하지 않는다). 종류가 없는 이전 결과는 재분석해야 집계된다(챗봇 유행 집계도 같다).
- **분류·속성은 그 옷 자체로 정한다**(문구는 `common.md`). 판매 구성(컬렉션·세트)이나 자료 전체 분위기에서 옮기지 않는다 — 셋업(SETUP)은 수트·트레이닝 셋업만이고 그 밖의 매칭 세트는 아이템별로 나눠 센다. 케이스마다 규칙을 늘리지 않고 원칙 한 줄 + 코드 이름의 범위(괄호)로 막는다.
- **요약은 유행이라고 단정하지 않는다**(문구는 `common.md`). 단정 문구가 RAG 검색 점수를 끌어올려 엉뚱한 근거가 뽑힌다. 유행 판단은 집계가 한다.
- **소재는 엄격하게** 뽑는다 — 틀린 소재보다 빈 배열이 낫다(정의서 P-05 소재별 집계가 틀린 값에 오염되므로). 주 소재(몸판·겉감)만, 텍스트는 본문에 직접 나온 것만, 이미지는 허용 목록 안에서 질감이 분명할 때만(문구는 `common.md`·`text.md`·`image.md`). 이미지 소재 언급량이 적게 잡히는 것은 의도된 것이다.
- **실루엣은 카테고리별 기준**(`silhouette.md`)으로 판단한다. 코드 11개를 핏(오버사이즈·레귤러·슬림)·기장(크롭·롱)·형태(박시·와이드·A·H라인·플레어·부츠컷) 세 축으로 나누고 축마다 최대 1개 — 같은 옷이 박시·오버사이즈·둘 다로 흩어지지 않게 한다. 정답셋 라벨도 이 기준을 쓴다. 공통코드에 실루엣 코드를 더하면 이 md에도 기준을 적는다.
  - "축마다 1개"는 프롬프트만으로 지켜지지 않아 **검증에서 강제**한다: 축마다 처음 값만 남긴다(실패로 돌리지 않음). 카테고리별로 쓸 수 없는 실루엣(하의 OVERSIZED, 원피스 CROPPED, 셋업 기장, 기타의 모든 실루엣)도 검증이 버린다.
  - 축과 쓸 수 있는 카테고리는 공통코드 `TREND_SILHOUETTE` 속성 `축,카테고리…`(예: `FIT,OUTER,TOP,DRESS,SETUP`, 카테고리를 안 적으면 전체 허용)로 정한다. 기존 DB 속성 보정은 [`admin-screens.md`](admin-screens.md).
- **패턴(무늬)**(공통코드 `TREND_PATTERN`: 무지·스트라이프·체크·플로럴·도트·애니멀·카모·페이즐리·아가일·그래픽·컬러 블록·기타, 사용자 요청)은 의류 아이템마다 0~1개다(값 종류 `PATTERN`) — 몸판에서 가장 눈에 띄는 무늬 하나, 무늬가 없으면 무지(SOLID). 무지도 값으로 둬 "무늬 없는 옷이 많다"도 센다. 질감(골지·퀼팅)·작은 로고·부분 배색은 무늬가 아니다(판단 문구는 `common.md`). 검증은 둘 이상이면 처음 것만, 패턴 칸이 없는 이전 결과는 빈 값. 주간 집계(P-05)·챗봇 집계(축·속성 조건 "체크 셔츠")·결과 팝업 "패턴" 칸·색인 요약에 쓴다. 기타 코드값은 `PATTERN_ETC`(다른 그룹의 ETC와 이름 목록이 겹치지 않게). 이미 분석된 문서는 재분석해야 값이 생긴다.
- **디자인 디테일**(공통코드 `TREND_DETAIL`, 사용자 요청)은 의류 아이템마다 0~3개다(값 종류 `DETAIL`). 축(속성) 넥라인·여밈·소매밑단·장식·짜임가공에 37개 + 기타(`DETAIL_ETC`). 전부 코드로 만들지 않고 자주 나오는 것만 두며, 기타가 자주 보이면 코드로 올린다. 아이템명·종류를 늘리지 않고 디테일을 따로 센다 — 종류 집계가 흩어지지 않게. 평범한 기본 요소(티셔츠의 라운드넥 등)는 쓰지 않는다(판단 문구는 `common.md`). 검증은 3개까지, 칸이 없는 이전 결과는 빈 값. 주간 집계·챗봇(묻는 축 "어떤 포인트"·속성 조건 "하프넥 니트")·결과 팝업 "디테일" 칸·색인 요약에 쓴다. 초안은 `TrendCodes.DETAIL_SEED`(Map.of 10쌍 제한으로 SEED 밖에 두고 합친다).
- **대상 라인**(공통코드 `TREND_GENDER`: 여성복·남성복·공용)은 의류 아이템마다 0~1개다(값 종류 `GENDER`). 입은 사람의 성별이 아니라 **판매되는 상품 라인**이다(사용자 결정) — 기획·MD가 라인별로 본다. 자료의 라인 표기(제목·본문·상품명)가 최우선이고, 표기가 없을 때만 모델 착장을 따른다 — 그것도 모델의 라인이 사진에서 분명할 때만이다. 얼굴이 잘려 체형·헤어·소품·분위기로 추측해야 하면 비운다(사용자 결정 — 남성복 쇼핑몰 사진을 토트백·실루엣으로 여성복이라 했다). 판단 문구는 `common.md`. 같은 청바지도 쇼핑몰마다 남성복·공용으로 갈려 사진만으로는 상품 라인을 알 수 없다 — 이미지만 있는 자료는 대상 정확도가 낮다. 검증은 둘 이상이면 처음 것만 남기고, 성별 칸이 없는 이전 AI 서비스 결과는 빈 값으로 받는다. 이미 분석된 문서는 재분석해야 값이 생긴다. 주간 집계(P-05)는 세지 않는다 — 챗봇 속성 조건("여성 아우터")과 결과 팝업 "대상" 칸에만 쓴다.
- **시즌**(공통코드 `TREND_SEASON`: 봄·여름·가을·겨울, 여러 개 가능)은 문서 단위다(판단 문구는 `text.md`·`image.md`·`article.md`). 판단할 수 없으면 비운다(검증도 빈 값을 허용한다).
- **공통코드 값**(코드 추가·이름 변경·사용 안 함)은 재기동 없이 다음 분석부터 적용된다(분석마다 읽는다). **코드 그룹(분류 축)**을 더하면 요청 형식이 바뀌므로 **Spring·AI 서비스 둘 다 재기동**한다 — 한쪽만 새 버전이면 분석이 전부 실패한다.
- **서버가 기계적으로 고칠 수 있는 지시는 프롬프트에 넣지 않는다**(빈 아이템 채우기, 종류–카테고리 짝 등은 검증이 한다). 단 서버는 틀린 값을 **버리기만** 하고 맞는 값으로 바꾸지 못하므로, 판단 기준(실루엣 정의 등)은 프롬프트에 둔다.
- **본문 + 이미지 원문은 Claude 호출 한 번**에 같이 보낸다(user: 이미지 → 본문 → 지시문 순). **본문이 주된 근거**다(우선순위 문구는 `article.md`). 시스템 프롬프트 조립 순서는 `common.md` 주석이 정본이다. 이미지 소재 허용 목록은 **이미지만 있는 원문에만** 건다 — 본문에 "울"이 나오면 써야 하므로.
  - 이미지가 여러 장이면 장마다 긴 변 1568px·3MB 이하로 줄인다(`image_prep.prepare(multiple=True)`) — 요청 전체 상한(32MB)을 넘지 않게. 사진 토큰은 크기에 비례한다(대략 가로×세로/750, 1568px 정사각이면 약 3,300).
- **이미지 소재는 허용 목록만**(공통코드 `TREND_MATERIAL` 속성 IMAGE: 레더·스웨이드·데님·니트·퍼·무스탕·플리스·트위드·코듀로이·새틴). 면·울·캐시미어·폴리에스터·실크·린넨·나일론·레이온·아크릴은 사진으로 가릴 수 없고 프롬프트로 막아도 추측하므로, 이미지 분석에는 이 목록만 허용 값으로 보내 스키마에서 막고 검증도 같은 목록으로 한다(`TrendCodeBook.restrict`). 텍스트는 전부 허용.
- **의류만** 뽑는다. 신발·가방·액세서리는 빼고, 카테고리 코드에도 두지 않는다(예전 DB에 남은 `SHOES`·`BAG`·`ACC`는 기동 때 `DataInitializer`가 지운다).
- **임베딩 모델은 `Qwen/Qwen3-VL-Embedding-2B`**다(한국어 질의 비교에서 후보 중 가장 잘 맞았다). 이 PC는 CPU로 돌아 느리다. 재검토 조건(제안값): `ai/evals/search_eval.py`에서 MRR이 0.7 미만이거나, 자료 없는 주제(negative) 1위 점수가 정답 문서 점수와 겹쳐 기준 0.60으로 갈리지 않으면 다른 후보를 같은 평가로 비교하고 사용자와 정한다. 모델을 바꾸면 새 컬렉션 + 재분석.
- **Chroma는 개발 중 내장형(`CHROMA_MODE=embedded`, `ai/chroma_data/`), 시스템 오픈(운영 배포) 때 서버형(`http`)**이다 — 이 결정의 정본은 여기다. 전환은 `ai/.env`의 `CHROMA_MODE=http`·`CHROMA_HOST`·`CHROMA_PORT`만 바꾼다(코드 수정 없음, Chroma 클라이언트는 `vector_store.create_client`에서만 만든다). 내장형 폴더의 색인은 서버로 옮겨지지 않지만, 다음 Spring 기동 때 색인 정리가 분석 완료 문서를 저장된 결과로 다시 색인한다([`document-upload.md`](document-upload.md)).

## 규칙

- **검증을 통과한 결과만 저장한다**(정의서 P-03). Structured Output이 형식을 맞춰 줘도 `TrendResultValidator`를 생략하지 않는다.
- **표준 코드 값만 저장한다.** 분석할 때마다 사용중 공통코드를 읽어 Claude 스키마 enum으로 넘긴다. 코드 이름의 괄호("레더(가죽)")는 다른 표기를 그 코드로 옮기는 힌트다.
- **분석 모델·감성(긍정·중립·부정)은 뽑지도 저장하지도 않는다**(사용자 결정 — 트렌드 판단에 쓰지 않는다). 쓰는 모델은 설정 `claude.structure-model`과 로그로 안다. 이전 DB의 `trend_items.model`·`sentiment` 컬럼은 기동 때 `DataInitializer.dropRetiredColumns`가 지운다(NOT NULL로 남으면 저장이 깨진다). 엔티티에서 컬럼을 빼면 여기에 같이 넣는다.
- **출처는 LLM이 만들지 않는다.** Spring이 원문 문서 값을 정형 JSON에 붙인다(정의서 10번 슬라이드 형식).
- **결과 형식·분류 축을 바꾸면 같이 고친다:** `ai/prompts/structure/*.md`(판단 규칙 — 공통·실루엣·이미지·텍스트·본문+이미지), `structurer.build_schema`, `TrendResultValidator`, `AnalysisService`(저장·정형 JSON), `indexer.summary_chunk`, `TrendItem.garments`, 집계(`TrendAggregationService.mentions`)와 근거 원문(`TrendQueryService.mentions`), 챗봇 유행 집계(`TrendFactsService`), 결과 모달(`trend-analysis.js`). 한 곳만 고치면 검증에서 전부 실패하거나 집계가 조용히 틀린다. **AI 서비스도 재기동**한다 — 옛 스키마로 떠 있으면 새 검증이 모든 결과를 거부한다.
- 아이템 수 상한(5)은 스키마로 걸 수 없다(구조화 출력은 배열 길이 제약 미지원). 프롬프트로 지시하고 검증에서 앞 5개만 남긴다.
- **소재 무스탕(`SHEARLING`)**은 몸판이 무스탕(양털 안감 가죽)일 때만 쓴다(주 소재 규칙). 질문 "무스탕 유행해?"는 이 소재 집계가 아니라 질문 단어(키워드·아이템명 언급)로 답한다([`rag-search.md`](rag-search.md)). 사진에서 양털 결이 보여 이미지 허용 소재다.
- **정답셋과 프롬프트는 같은 분류 기준을 쓴다**(사용자 결정). 레더 아우터·니트 범위·일부만 보이는 옷·데님 워싱 색·명암·무늬 색 규칙의 문구는 `common.md`·`image.md`·`silhouette.md`에만 둔다. 데님 워싱은 연청·중청 BLUE, 진청·생지 NAVY, 블랙진 BLACK이고 컬러 데님 코드는 두지 않는다. 기존 원문은 재분석해야 새 기준으로 바뀐다.
- **정형화 정확도 평가**: 정답셋 `ai/evals/structure_gold.json`을 `ai/evals/structure_eval.py`로 실제 이미지 정형화에 돌려 아이템별로 맞댄다(사진 1장 약 $0.006). 정답을 고쳤으면 `--rescore`로 저장된 예측을 다시 채점한다(비용 없음). 정답의 `null` 칸은 채점하지 않는다.
  - 정답셋은 사람이 엑셀로 단 라벨이다 — `py ai/evals/gold_from_excel.py "<엑셀>" "<이미지 폴더>"`로 옮긴다(엑셀 이름 → 공통코드 코드값, 코드에 없는 값이 있으면 멈춘다). 사진은 `ai/evals/gold/images/`(커밋 제외)에 번호 이름·실제 형식 확장자로 복사한다.
  - 채점은 정답셋에 적힌 옷만 한다(사용자 결정) — 정답은 사진마다 판매 상품만 적어서, 같이 입은 옷을 더 찾은 예측은 감점하지 않는다(결과의 extra로만 남긴다).
  - 라벨도 앱 규칙을 따라야 한다(실루엣 축마다 1개·카테고리별로 쓸 수 있는 실루엣·종류와 카테고리 일치) — 앱이 낼 수 없는 정답은 정확도만 깎는다.
  - 소재 정답은 사진 질감 기준이다(사용자 결정). 엑셀 소재는 상품 페이지의 섬유 성분(청바지 = 면)이라, 변환할 때 종류·아이템 이름에서 질감 소재(데님·플리스·니트·레더·스웨이드·시어링·코듀로이)를 더한다(`gold_from_excel.py`). 채점은 이미지 허용 소재(속성 IMAGE)만 본다.
  - 대상 정답은 상품 라인(엑셀 그대로)이다.
  - 점수는 실행마다 흔들린다 — 규칙을 비교할 때는 같은 규칙을 2~3번 돌려 평균으로 본다.
- **분석 결과 조회 화면**(`analysis-result`, 사용자 요청): 분석이 끝난 원문을 최근 것부터 한 줄씩 — 카테고리·키워드·컬러·패턴·실루엣(코드 대신 이름). 헤더를 누르면 정렬한다. **사진은 그리드에 두지 않고 행을 눌러 팝업을 열 때만 받는다**(사용자 결정 — 목록에서 한꺼번에 받으면 느리다). 조회 조건은 카테고리·종류(`TREND_CATEGORY`·`TREND_ITEM`)이고, 조건에 맞는 의류 아이템이 있는 원문만, 값은 그 아이템들의 값만 보인다(키워드는 원문 단위). **행을 누르면 팝업에 사진을 크게**(사진 없는 텍스트 원문은 안내 문구)와 출처·종류·값을 보인다. 사진은 이미지 원문의 사진, 텍스트 원문은 첫 첨부 사진 — 이미지 업로드 권한 없이 보이도록 `GET /api/analysis-results/{docId}/image`로 따로 연다(분석 완료 원문만). 거르기·최근 게시일 순·페이지(100건씩, 최대 500)는 DB가 한다(`SourceDocumentRepository.findAnalyzed`) — 헤더 정렬은 지금 페이지 안에서만이다. 테스트 `AnalysisResultApiTest`.
- **업로드 화면 결과 팝업에도 원문의 사진을 보인다**: 이미지 원문은 분석한 그 사진을 크게, 텍스트 원문은 첨부 이미지를 작게(`AnalysisView.images`). 누르면 원본을 새 창으로 연다.
- 결과 팝업의 의류 아이템 표에는 **아이템명을 보이지 않는다**(사용자 결정 — 종류와 뜻이 겹쳐 헷갈린다). 아이템명은 데이터로만 남아 색인 요약 청크와 챗봇 유행 집계(기타 값의 아이템명 상위·질문 단어·대상 옷 포인트 — [`rag-search.md`](rag-search.md))에 쓰고, 정형 JSON 보기에는 원본 그대로 있다. 주간 집계(P-05)는 세지 않는다.
- 저장: 아이템 단위 값(아이템명 `ITEM`·소재·컬러·실루엣)은 `trend_item_values`의 `garment_no`·`category`로 묶는다. `trend_items.category`는 대표(첫) 아이템이다 — NOT NULL 컬럼이라 엔티티에서 빼면 `ddl-auto=update`가 컬럼을 지우지 않아 저장이 깨진다.
- 아이템 배열 이전 결과(`garment_no` 없음)는 `TrendItem.garments()`가 문서 카테고리로 아이템 하나를 만들어 보여 준다. 재분석하면 새 형식이 된다.
- **일괄 재분석**(사용자 요청): 이미지 업로드(기타2)·텍스트 등록(기타1)의 "재분석" 버튼이 체크한 원문을 한 번에 대기열에 넣는다(`POST /api/images/reanalyze`·`/api/texts/reanalyze`, ID 목록). 규칙·코드가 바뀐 뒤 기존 원문을 새 기준으로 다시 분석할 때 쓴다. 한 번에 200건까지(`DocumentService.MAX_BULK_REANALYZE` — 실수로 전체를 눌러 비용이 크게 나가지 않게), 이미 대기·분석 중인 원문은 건너뛰고 건수를 알린다. 화면은 건수와 대략의 비용(건당 약 10원)을 묻는다. 기존 DB는 기동 때 그 기타 버튼 이름이 비어 있으면 "재분석"을 넣는다(admin은 모든 버튼 권한, 다른 사용자는 사용자별 권한관리). 테스트 `BulkReanalyzeApiTest`.
- 실패는 예외로 끝내지 않고 문서 `FAILED`·사유로 남겨 화면에서 재분석하게 한다. 재시도 가능(연결·429·5xx·형식 오류)과 불가(키 오류·거절)를 구분한다 — FastAPI 오류 본문 `{"detail": {"message", "retryable", "usage"?}}`.
- **Claude 키는 요청 헤더로만** AI 서비스에 넘긴다. 로그·응답·예외 메시지에 넣지 않는다. AI 서비스는 127.0.0.1에만 연다(인증 없는 내부 API — 다른 서버로 분리하면 내부 토큰·TLS부터).
- 외부 호출은 트랜잭션 밖, 트렌드 항목 저장만 짧은 트랜잭션.
- 색인 청크: 문서마다 정형 결과를 **코드값 대신 이름**으로 쓴 요약 청크 1개(한국어 질문과 맞추려고) + 텍스트는 본문 청크(500자/80자 겹침). 재분석이면 그 문서 청크를 갈아끼운다.
- 임베딩은 문서는 그대로, **질의에만 영어 지시문**을 붙인다(Qwen 모델 카드 권장, Chroma가 질의 때 `embed_query`를 부른다).
- 컬렉션에 임베딩 모델을 기록하고, 다른 모델로 열면 기동을 막는다(섞이면 검색이 조용히 틀린다). 모델을 바꾸면 새 컬렉션 + 재분석.
- **정형화 요청은 고정 부분을 프롬프트 캐싱한다**(사용자 결정). 규칙·허용 코드 목록·스키마(약 6,000토큰)는 매번 같아서, 허용 코드 목록도 system에 두고 system 마지막 블록에 캐시 표시를 단다 — 이미지·본문·지시문만 user에 남는다. 캐시는 **5분** 유지라 이어서 여러 건 분석(재분석·일괄 업로드)할 때 이득이고, 띄엄띄엄 한 건씩이면 쓰기 비용(입력 단가의 1.25배)만 더 든다. 모델·자료 유형(이미지만·본문만·본문+이미지)·공통코드가 바뀌면 새 캐시다. 그래서 **system에 날짜·문서 값 같은 바뀌는 값을 넣지 않는다.**
- **캐시가 식었으면 한 건만 먼저 보낸다**(`CacheWarmGate`, 사용자 요청): 분석 스레드 2개가 동시에 보내면 캐시가 아직 없어 둘 다 캐시를 만든다(캐시는 첫 응답이 나와야 쓸 수 있다). 프롬프트 종류(모델 + 이미지만·본문만·본문+이미지)마다 4분 안에 성공한 호출이 없으면 한 건만 먼저 보내고, 같은 종류의 나머지는 그 건이 끝날 때까지(최대 3분) 기다렸다가 캐시를 읽는다. 데우던 건이 실패하면 기다리던 건이 이어 데운다. 다른 종류는 서로 기다리지 않는다.
- 토큰은 과금 근거라 호출마다 로그에 남긴다. 응답 뒤 실패(거절·잘림·JSON 오류)도 토큰이 과금되므로 오류 본문 `usage`로 넘겨 누적에 넣는다.

## 주의점

- 서버가 분석 도중 내려가면 PENDING·PROCESSING이 남는다 — 기동 직후 PROCESSING을 PENDING으로 돌리고 PENDING을 다시 대기열에 넣는다.
- **분석은 PENDING → PROCESSING으로 바꾼 요청만 맡는다**(`SourceDocumentRepository.changeStatus`, 조건부 update). 같은 문서가 대기열에 두 번 실리면(등록 이벤트와 기동 재대기가 겹칠 때) 두 번째는 건너뛴다 — 끝난 문서를 다시 분석하면 Claude 호출이 낭비된다. 재분석은 먼저 PENDING으로 바꾸므로 그대로 된다.
- 분석 스레드는 2개뿐이다(Claude 429·내장형 Chroma 동시 쓰기를 줄이려고). 나머지는 대기열에서 기다린다.
- `AiClient`는 java.net.http + **HTTP/1.1**이다. `HttpURLConnection`은 401 본문(실패 사유)을 버렸고, HTTP/2 업그레이드는 uvicorn이 본문을 못 받아 422가 났다. 요청 본문은 chunked로 간다(Content-Length 없음).
- CPU 임베딩은 청크 수에 비례해 느려서, 본문이 긴 텍스트는 색인이 Spring의 AI 응답 대기(읽기 타임아웃 3분)를 넘겨 문서가 `FAILED`("색인(P-04) 실패")로 남을 수 있다. 몇 자부터 넘는지는 재지 않았다(미측정).
- 저해상도 이미지는 소재(데님 결 등)를 놓친다.
- Claude가 값을 고른 근거는 출력 스키마에 칸이 없어 저장하지 않는다(미구현 — 필요하면 스키마·검증·저장을 같이 고친다).
- 이미지 자체는 임베딩하지 않는다(미구현). 사진 원문은 정형 결과 요약 청크로만 검색된다.
- 누적 토큰은 메모리 값이라 재기동하면 0부터다.

## 확인할 것

- 분석 흐름 테스트는 문서를 저장소에 바로 넣고 `analyze(id)`를 직접 부른다(등록 API로 넣으면 분석 스레드와 겹친다).
- 연결 확인: 일부러 틀린 키로 문서를 올려 "Claude API 키가 올바르지 않습니다"로 실패하면 Spring → FastAPI → Claude까지 연결된 것이다. "AI 서비스에 연결하지 못했습니다"면 `ai/start-ai.cmd`.
- 색인 데이터는 AI 서비스의 `/docs` → `GET /index/stats`·`/index/chunks`로 본다.
