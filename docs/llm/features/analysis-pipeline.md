# analysis-pipeline.md — AI 분석 (P-03 정형화 · P-04 저장·색인)

원문 한 건을 Claude로 정형화(의류 아이템별 카테고리·종류·소재·컬러·실루엣 + 문서 단위 키워드·시즌·요약)하고, 검증해 RDB에 저장한 뒤 Chroma에 색인한다. Spring과 AI 서비스(`ai/`)에 걸친 기능이다.
코드: `service/analysis`(`AnalysisService` 흐름, `TrendResultValidator` 검증, `AiClient` 호출), `ai/app/structuring/structurer.py`·`ai/app/indexing/`(`indexer`·`embedding`·`vector_store.py`. 실행·설정은 [`ai-development.md`](../ai/ai-development.md).

## 결정 사항 (2026-10-20 사용자)

- AI 처리는 Python **FastAPI 서버**로 띄우고 Spring이 호출한다.
- LLM은 `claude-sonnet-5`(`claude.model`). 키는 Spring `claude.api.key` **한 곳**에만 둔다.
- 표준 코드(카테고리·소재·컬러·실루엣)는 일반 분류 **초안**이다. 확정 체계는 미정(정의서 미결 4번).
- **정형 결과는 의류 아이템 배열**(`items: [{category, item, type, materials, colors, silhouettes}]`)이다. 정의서 10번 형식(문서당 category 1개)에서 벗어난다 — 코디 사진은 아이템이 여럿이라 한 묶음으로 받으면 속성이 섞인다.
- **아이템 종류(`type`, 공통코드 `TREND_ITEM`)**를 아이템마다 고른다(2026-10-22 사용자 결정). 유행 = 많이 입는 것을 세려면 아이템명(Claude 자유 문장)은 "데님 트러커 재킷"·"트러커 재킷"으로 갈라져서, 정한 목록(패딩·블루종·데님 재킷… 카테고리마다 기타 포함)에서 고르게 한다. 코드값은 `카테고리_종류`(OUTER_PADDING)라 아이템 카테고리와 어긋나면 검증이 **종류의 카테고리로 맞춘다**(재시도하지 않는다). 핏·기장은 종류가 아니라 실루엣. 예전 결과는 종류가 없어 재분석해야 집계된다(챗봇 유행 집계도 같다).
- **분류·속성은 그 옷 자체로 정한다**(2026-10-23 사용자 결정). 컬렉션·세트 같은 판매 구성이나 자료 전체 분위기에서 옮기지 않는다 — "컬렉션은 화이트 중심"만 있는 아이템은 색을 비우고, **셋업(SETUP)은 수트·트레이닝 셋업만** 쓴다(플리스·니트 매칭 세트는 아우터·상의와 하의로 나누고 세트라는 점은 키워드로). 케이스마다 규칙을 늘리지 않고 원칙 한 줄 + 코드 이름의 범위(괄호)로 막는다. 실측: TXT-20261023-000106(스노우피크×헬로키티) — 세 번 모두 플리스 재킷(OUTER_FLEECE)+팬츠로 나뉘고 본문에만 나온 상의 색이 비었다.
- **요약은 유행이라고 단정하지 않는다**(`structure/common.md`): 사진 한 장으로 "트렌드로 보인다"고 쓰면 그 문구가 RAG 검색 점수를 끌어올려 엉뚱한 근거가 뽑혔다. 유행 판단은 집계가 한다.
- **소재는 빼지 않되 엄격하게** 뽑는다: 텍스트는 본문에 그 아이템의 소재가 직접 나온 것만, 이미지는 아래 허용 목록 안에서 질감이 분명할 때만. 애매하면 빈 배열 — 틀린 소재보다 비는 게 낫다(정의서 P-05가 소재별 집계를 쓴다). **주 소재(몸판·겉감)만** 쓰고 트리밍·포켓 장식·안감·스트랩처럼 일부에만 쓴 소재는 뺀다(2026-10-23 — "레더 트리밍 포켓"이 레더 재킷으로 세졌다). 이미지 소재 언급량이 적게 잡히는 것은 의도된 것이다.
- **실루엣은 카테고리별 기준**(`ai/prompts/structure/silhouette.md`)으로 판단한다. 코드 10개를 핏(오버사이즈·레귤러·슬림)·기장(크롭·롱)·형태(박시·와이드·A·H라인·플레어) 세 축으로 나누고 축마다 최대 1개 — 같은 옷이 박시·오버사이즈·둘 다로 흩어지던 것을 막는다. 정답셋 라벨도 이 기준을 쓴다. 공통코드에 실루엣 코드를 더하면 이 md에도 기준을 적는다.
  - "축마다 1개"는 프롬프트만으로 지켜지지 않아(오버사이즈·레귤러 동시 출력 확인) **검증에서 강제**한다: 축마다 처음 값만 남긴다(실패로 돌리지 않음). 카테고리별로 쓸 수 없는 실루엣(하의 OVERSIZED, 원피스 CROPPED, 셋업 기장, 기타의 모든 실루엣)도 검증이 버린다.
  - 축과 쓸 수 있는 카테고리는 공통코드 `TREND_SILHOUETTE` 속성 `축,카테고리…`(예: `FIT,OUTER,TOP,DRESS,SETUP`, 카테고리를 안 적으면 전체 허용)로 정한다. 예전 DB의 축만 있는 속성은 기동 때 기본값으로 늘린다(화면에서 다르게 고친 값은 그대로).
- **시즌**(공통코드 `TREND_SEASON`: 봄·여름·가을·겨울, 여러 개 가능)은 문서 단위다. 텍스트는 본문에 나온 시즌("올가을", "26SS")을 먼저, 없으면 아이템 두께로 판단하고, 이미지는 옷의 두께·레이어링으로 판단한다. 판단할 수 없으면 비운다(검증도 빈 값을 허용한다).
- **공통코드 값**(코드 추가·이름 변경·사용 안 함)은 재기동 없이 다음 분석부터 적용된다(분석마다 읽는다). **코드 그룹(분류 축)**을 더하면 요청 형식이 바뀌므로 **Spring·AI 서비스 둘 다 재기동**한다 — 한쪽만 새 버전이면 분석이 전부 실패한다.
- **서버가 기계적으로 고칠 수 있는 지시는 프롬프트에 넣지 않는다**(2026-10-22 사용자 결정 — 빈 아이템 채우기, 종류–카테고리 짝 등은 검증이 한다). 단 서버는 틀린 값을 **버리기만** 하고 맞는 값으로 바꾸지 못하므로, 판단 기준(실루엣 정의 등)은 프롬프트에 둔다.
- **본문 + 이미지 원문은 Claude 호출 한 번**에 같이 보낸다(이미지 → 본문 → 지시문 순). **본문이 주된 근거**다 — 본문과 사진이 다르면 본문, 같은 아이템은 하나로 합친다(우선순위 규칙은 `structure/article.md`, 마지막 지시문도 본문 우선). 시스템 프롬프트는 공통 → 실루엣 → 텍스트 기준 → 이미지 기준 → `article.md` 순으로 붙인다. 이미지 소재 허용 목록은 **이미지만 있는 원문에만** 건다 — 본문에 "울"이 나오면 써야 하므로.
  - 이미지가 여러 장이면 장마다 긴 변 1568px·3MB 이하로 줄인다(`image_prep.prepare(multiple=True)`) — 요청 전체 상한(32MB)을 넘지 않게. 사진 토큰은 크기에 비례한다(대략 가로×세로/750 — 332×677 사진은 약 300, 1568px 정사각이면 약 3,300).
- **이미지 소재는 허용 목록만**(공통코드 `TREND_MATERIAL` 속성 IMAGE: 레더·스웨이드·데님·니트·퍼·플리스·트위드·코듀로이·새틴, 2026-10-20 사용자 결정). 면·울·캐시미어·폴리에스터·실크·린넨·나일론은 사진으로 가릴 수 없는데 프롬프트로 막아도 면을 추측했다 — 그래서 이미지 분석에는 이 목록만 허용 값으로 보내 스키마에서 막고, 검증도 같은 목록으로 한다(`TrendCodeBook.restrict`). 텍스트는 전부 허용.
- **의류만** 뽑는다. 신발·가방·액세서리는 뺀다. 카테고리 코드 초안에서도 SHOES·BAG·ACC를 뺐다 — 이미 넣은 DB는 공통코드 관리에서 사용 안 함으로 바꾼다.
- 임베딩은 "일단" `Qwen/Qwen3-VL-Embedding-2B`. 한국어 질의 비교에서 3/3(mpnet 2/3, e5-large 1/3, Chroma 기본 영어 MiniLM 실패). 이 PC는 CPU로 돌아 느리다.
- Chroma는 지금 내장형, 시스템 오픈 때 서버형. 전환은 `ai/.env`의 `CHROMA_MODE`만 바꾼다.

## 규칙

- **검증을 통과한 결과만 저장한다**(정의서 P-03). Structured Output이 형식을 맞춰 줘도 `TrendResultValidator`를 생략하지 않는다.
- **표준 코드 값만 저장한다.** 분석할 때마다 사용중 공통코드를 읽어 Claude 스키마 enum으로 넘긴다. 코드 이름의 괄호("레더(가죽)")는 다른 표기를 그 코드로 옮기는 힌트다.
- **분석 모델·감성(긍정·중립·부정)은 뽑지도 저장하지도 않는다**(2026-10-23 사용자 결정 — 사용자에게 필요 없고 트렌드 판단에 쓰지 않는다). 쓰는 모델은 설정 `claude.model`과 로그로 안다. 예전 DB의 `trend_items.model`·`sentiment` 컬럼은 기동 때 `DataInitializer.dropRetiredColumns`가 지운다(NOT NULL로 남으면 저장이 깨진다). 엔티티에서 컬럼을 빼면 여기에 같이 넣는다.
- **출처는 LLM이 만들지 않는다.** Spring이 원문 문서 값을 정형 JSON에 붙인다(정의서 10번 슬라이드 형식).
- **결과 형식·분류 축을 바꾸면 같이 고친다:** `ai/prompts/structure/*.md`(판단 규칙 — 공통·실루엣·이미지·텍스트·본문+이미지), `structurer.build_schema`, `TrendResultValidator`, `AnalysisService`(저장·정형 JSON), `indexer.summary_chunk`, `TrendItem.garments`, 집계(`TrendAggregationService.mentions`)와 근거 원문(`TrendQueryService.mentions`), 챗봇 유행 집계(`TrendFactsService`), 결과 모달(`trend-analysis.js`). 한 곳만 고치면 검증에서 전부 실패하거나 집계가 조용히 틀린다. **AI 서비스도 재기동**한다 — 옛 스키마로 떠 있으면 새 검증이 모든 결과를 거부한다.
- 아이템 수 상한(5)은 스키마로 걸 수 없다(구조화 출력은 배열 길이 제약 미지원). 프롬프트로 지시하고 검증에서 앞 5개만 남긴다.
- **소재 무스탕(`SHEARLING`, 2026-10-23 사용자 결정)**: 몸판이 무스탕(양털 안감 가죽)일 때만 쓴다. 무스탕 칼라만 달린 레더 재킷은 주 소재 규칙으로 LEATHER만 — 질문 "무스탕 유행해?"는 이 소재 집계가 아니라 질문 단어(키워드·아이템명 언급)로 답한다([`rag-search.md`](rag-search.md)). 사진에서 양털 결이 보여 이미지 허용 소재(속성 IMAGE)다.
- 결과 팝업의 의류 아이템 표에는 **아이템명을 보이지 않는다**(2026-10-23 사용자 결정 — 종류와 뜻이 겹쳐 헷갈린다). 아이템명은 데이터로만 남아 챗봇의 기타 종류 설명·집계에 쓴다(정형 JSON 보기에는 원본 그대로 있다).
- 저장: 아이템 단위 값(아이템명 `ITEM`·소재·컬러·실루엣)은 `trend_item_values`의 `garment_no`·`category`로 묶는다. `trend_items.category`는 대표(첫) 아이템이다 — NOT NULL 컬럼이라 엔티티에서 빼면 `ddl-auto=update`가 컬럼을 지우지 않아 저장이 깨진다.
- 아이템 배열 이전 결과(`garment_no` 없음)는 `TrendItem.garments()`가 문서 카테고리로 아이템 하나를 만들어 보여 준다. 재분석하면 새 형식이 된다.
- 실패는 예외로 끝내지 않고 문서 `FAILED`·사유로 남겨 화면에서 재분석하게 한다. 재시도 가능(연결·429·5xx·형식 오류)과 불가(키 오류·거절)를 구분한다 — FastAPI 오류 본문 `{"detail": {"message", "retryable", "usage"?}}`.
- **Claude 키는 요청 헤더로만** AI 서비스에 넘긴다. 로그·응답·예외 메시지에 넣지 않는다. AI 서비스는 127.0.0.1에만 연다(인증 없는 내부 API — 다른 서버로 분리하면 내부 토큰·TLS부터).
- 외부 호출은 트랜잭션 밖, 트렌드 항목 저장만 짧은 트랜잭션.
- 색인 청크: 문서마다 정형 결과를 **코드값 대신 이름**으로 쓴 요약 청크 1개(한국어 질문과 맞추려고) + 텍스트는 본문 청크(500자/80자 겹침). 재분석이면 그 문서 청크를 갈아끼운다.
- 임베딩은 문서는 그대로, **질의에만 영어 지시문**을 붙인다(Qwen 모델 카드 권장, Chroma가 질의 때 `embed_query`를 부른다).
- 컬렉션에 임베딩 모델을 기록하고, 다른 모델로 열면 기동을 막는다(섞이면 검색이 조용히 틀린다). 모델을 바꾸면 새 컬렉션 + 재분석.
- **정형화 요청은 고정 부분을 프롬프트 캐싱한다**(2026-10-22 사용자 결정). 규칙·허용 코드 목록·스키마(약 6,000토큰)는 매번 같아서, 허용 코드 목록도 system에 두고 system 마지막 블록에 캐시 표시를 단다 — 이미지·본문·지시문만 user에 남는다. 캐시는 **5분** 유지라 이어서 여러 건 분석(재분석·일괄 업로드)할 때 이득이고, 띄엄띄엄 한 건씩이면 쓰기 비용(입력 단가의 1.25배)만 더 든다. 모델·자료 유형(이미지만·본문만·본문+이미지)·공통코드가 바뀌면 새 캐시다. 그래서 **system에 날짜·문서 값 같은 바뀌는 값을 넣지 않는다.**
- 토큰은 과금 근거라 호출마다 로그에 남긴다. 응답 뒤 실패(거절·잘림·JSON 오류)도 토큰이 과금되므로 오류 본문 `usage`로 넘겨 누적에 넣는다.

## 주의점

- 서버가 분석 도중 내려가면 PENDING·PROCESSING이 남는다 — 기동 직후 PROCESSING을 PENDING으로 돌리고 PENDING을 다시 대기열에 넣는다.
- **분석은 PENDING → PROCESSING으로 바꾼 요청만 맡는다**(`SourceDocumentRepository.changeStatus`, 조건부 update). 같은 문서가 대기열에 두 번 실리면 두 번째는 건너뛴다 — 2026-10-23 샘플 37건이 등록 이벤트와 기동 재대기에 함께 실려 이미 끝난 문서를 다시 분석했다(Claude 호출 낭비). 재분석은 먼저 PENDING으로 바꾸므로 그대로 된다.
- 분석 스레드는 2개뿐이다(Claude 429·내장형 Chroma 동시 쓰기를 줄이려고). 나머지는 대기열에서 기다린다.
- `AiClient`는 java.net.http + **HTTP/1.1**이다. `HttpURLConnection`은 401 본문(실패 사유)을 버렸고, HTTP/2 업그레이드는 uvicorn이 본문을 못 받아 422가 났다. 요청 본문은 chunked로 간다(Content-Length 없음).
- CPU 임베딩은 느려서, 본문이 길어 청크가 많은 텍스트는 색인이 Spring 응답 대기(3분)를 넘겨 "색인 실패"로 남을 수 있다(청크 수에 비례 — 넘기는 길이는 아직 재지 않았다).
- 저해상도 이미지는 소재(데님 결 등)를 놓친다. 판단 근거는 지금 저장하지 않는다.
- 이미지 자체 임베딩은 아직 안 한다(요약 문장만 색인).
- 누적 토큰은 메모리 값이라 재기동하면 0부터다.

## 확인할 것

- 분석 흐름 테스트는 문서를 저장소에 바로 넣고 `analyze(id)`를 직접 부른다(등록 API로 넣으면 분석 스레드와 겹친다).
- 연결 확인: 일부러 틀린 키로 문서를 올려 "Claude API 키가 올바르지 않습니다"로 실패하면 Spring → FastAPI → Claude까지 연결된 것이다. "AI 서비스에 연결하지 못했습니다"면 `ai/start-ai.cmd`.
- 색인 데이터는 AI 서비스의 `/docs` → `GET /index/stats`·`/index/chunks`로 본다.
