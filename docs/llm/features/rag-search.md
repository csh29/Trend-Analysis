# rag-search.md — P-06 RAG 검색 (홈 트렌드 챗봇)

질문 → 해석 → (유행 질문) 도구 경로 — Claude가 집계 도구를 불러 답 / (그 밖) 근거 검색 → Claude 답변 + 출처. 홈 트렌드 챗봇(`home.html`, API `POST /api/rag/ask`).
코드: Spring `service/rag/`(`RagService` 흐름, `AgentService` 도구 경로, `QuestionInterpreter` 규칙 해석·기간, `TrendFactsService` 유행 집계), AI `ai/app/rag/`(`interpret` 질문 해석, `agent` 도구 경로 한 단계, `answer` 검색·답변), 프롬프트 `ai/prompts/rag/interpret.md`·`agent.md`·`answer.md`.

## 결정 사항 (사용자)

- **경향은 집계로만 말한다**(사용자 결정 — 분석 시스템이다): 경향·특징·방향·추천·정리·비교를 묻는 질문은 모두 유행 질문(집계)이다. 검색은 사례 자체(코디·레퍼런스·특정 자료·정의)를 원할 때만 쓰고, 검색 답은 사례 소개로만 쓰며 경향으로 일반화하지 않는다. 핵심·주요·대세라고 쓰는 값은 유행점수 2 이상(출처 2곳 이상 또는 같은 출처 3건 이상)만이고, 원문 1건뿐인 값은 "사례"로만 쓴다.
- **질문 유형마다 칸·규칙을 두지 않는다**(2026-10-29 사용자 결정 — AI로 자동화하려는 것이다): 유행 질문은 모두 도구 경로로 보내 Claude가 무엇을 셀지 고른다("패딩 제외하고", "두 시즌 비교", "6주 추이"). 답변 규칙(`answer.md` system_trend)은 질문 유형별 케이스가 아니라 원칙(집계로만 판단·유행점수 순·숫자는 질문이 원할 때만·기타 묶음은 순위 밖·내부 사정 쓰지 않기)만 둔다.
- **답 형식은 질문을 따른다**(사용자 요청): 기본은 결론 한 줄(summary) + 글머리 줄(points). 질문이 형식(표로·비교표·문단으로·N줄로·번호 목록)을 요구하거나 비교·브리프처럼 표가 나은 답이면 자유 형식 본문(`body` — 표·목록·소제목·**굵게**·문단, 마크다운 일부)으로 쓰고 points는 비운다. 본문도 행·줄마다 [n] 근거 번호를 붙이고, 없는 번호는 AI 서비스와 Spring이 지운다(본문의 번호도 출처가 된다). 인용한 번호가 모두 없는 번호인 줄은 줄째 뺀다(아래 "규칙"). 화면(`home.html renderBody`)은 innerHTML 없이 텍스트 노드로만 그린다 — 대괄호+여는 괄호는 Thymeleaf 인라인 문법이라 정규식에 `\x5B`로 쓴다.
- **숫자는 질문이 원할 때만 쓴다**(사용자 결정): 무엇이 유행인지·어떤 특징인지만 물으면 건수·출처 수·유행점수·증감 없이 답한다 — 순위는 위에서부터 "값: 특징"으로 최대 5개, 특징은 컬러·패턴·실루엣·소재·디테일·코디. 숫자는 답 아래 판단 근거 막대가 보인다. 증감·비교·추이·건수·브리프·표를 물으면 집계 값을 그대로 쓴다(증감률은 서버가 계산한 값을 옮긴다).

- **LangChain은 쓰지 않는다.** 검색·답변 몇 번이라 Anthropic SDK를 바로 부른다(정형화와 같은 방식). 답변 모델은 `claude.model`(`claude-sonnet-5`).
- 범위는 질문·답변·출처까지. **답변 만족도 평가는 P-08 때.** 질문·답변을 저장하지 않는다.
- **별도 화면 없이 홈에 둔다**(요약 카드 아래). 프로그램 `rag-search`는 쓰지 않으며, 남아 있으면 기동 때 `DataInitializer`가 지운다.
- **유행 = 많은 사람이 입어 대중화된 것.** 그래서 **유행 질문은 개수(원문 수·출처 수)로 답한다** — 문장 유사도로 고른 자료 몇 건으로 "유행"이라고 하지 않는다.
- **질문 해석은 AI(작은 모델)가 한다.** 규칙은 미리 넣은 말만 알아듣기 때문이다. 해석 호출이 실패하면 규칙으로 대신한다(답변이 멈추지 않게). 해석은 패션 질문인지·유행 질문인지(경로)와, 도구 경로가 실패했을 때의 고정 경로 범위·화면 표시에 쓴다.
- **패션·트렌드 질문이 아니면 답하지 않는다.** 유행 질문은 유사도 검사를 거치지 않아, 막지 않으면 "요즘 유행하는 밈은?"에도 옷 원문을 세서 답한다. 판단은 해석 호출의 `fashion` 칸으로 한다(호출을 늘리지 않는다).
- **화면은 대화형 챗봇**이고 **이어 묻기**("그럼 하의는?")를 알아듣는다. 대화는 화면에만 있고 저장하지 않는다(새로 열거나 지우면 사라짐).

## 질문 해석

- **AI 해석**(`/interpret`, `claude.interpret-model` 기본 `claude-haiku-5-5`, effort low): 질문(+ 앞 대화) → {다시 쓴 질문, 패션 질문인지, 유행 질문인지, 카테고리, 아이템 종류, 기간, 질문 단어, 시즌, 묻는 축, 속성 조건}. 판단 기준 문장은 `interpret.md`에만 둔다.
  - **해석 입력은 캐시하지 않는다**(사용자 결정 — 챗봇은 5분 안에 이어 묻는 일이 많지 않을 것이라, 캐시를 만드는 1.25배 비용이 손해가 될 수 있다). 규칙(`interpret.md`)과 허용 코드 목록은 system, 날짜·앞 대화·질문은 user에 둔다. 출력 스키마에는 enum을 싣지 않는다(목록 밖 값은 `normalize`와 Spring이 버린다). 실제 사용 로그에서 질문 5개 중 1개 이상이 앞 질문 5분 안에 오면 캐시를 다시 검토한다(본전 기준 약 22%).
  - **판단이 필요 없는 규칙은 코드가 보장한다**(2026-10-29 입력 토큰 최적화 — `interpret.normalize`, 프롬프트에서 뺐다): 표준 기간 표현의 날짜 계산(`standard_period` — 지난주·이번 주·지난달·이번 달·최근 N일/주/개월·올해·작년·시즌 표현 183일, Spring `QuestionInterpreter`와 같은 규칙. 바로 뒤에 "대비·보다·비해"가 붙으면 비교 기준이라 기간 없음. 두 해를 비교하거나 "작년 F/W"처럼 해와 시즌이 겹치면 모델 값을 쓴다), 패션 외 질문의 나머지 칸 비우기, 종류 → 카테고리, 묻는 축의 값 빼기, 종류 이름에 든 소재 빼기(데님 팬츠 → DENIM), 앞 대화가 없으면 질문 그대로, terms의 축 이름·일반어·시즌 말·카테고리 말 거르기. 첫 질문 입력 약 8,070 → 6,070토큰(규칙 4,362 → 2,356, 코드 목록 2,644·출력 스키마 1,003은 그대로), 이어 묻기 약 8,790 → 6,740. 15문항 회귀(2회씩)에서 240필드 중 237 일치 — 다른 3개는 시즌 기간을 183일로 바로잡은 2건과 "여성 아우터 트렌드"의 묻는 축(없음 → 아이템 종류).
  - **2단계 — 모델은 이름을 고르고 코드가 코드값으로 바꾼다**(2026-10-29 사용자 요청): 허용 값 목록은 이름만 싣고(영문 코드값 없음, `allowed_values_text`), `normalize`가 이름·괄호 안 같은 뜻 말·코드값을 코드값으로 바꾼다(`_pick`·`_attributes`). 디테일 목록(약 800토큰)은 질문(이어 묻기면 앞 질문까지)에 디테일 말(디테일·포인트·넥·소매·포켓…)이나 디테일 이름·같은 뜻 말이 있을 때만 보낸다 — 종류 이름 속 말(카고 팬츠의 "카고", 후드티의 "후드")은 빼고 본다. 출력 스키마는 enum을 빼고(칸 하나 약 25토큰, enum은 값마다 더 든다 — 카테고리 85·축 110·시즌 86토큰이었다) 기간 4칸 → `period` 한 칸("YYYY-MM-DD~YYYY-MM-DD 이름"), 속성 6칸 → `attributes` 한 칸, `question`은 앞 대화가 있을 때만 받는다. 시즌 약어(F/W·S/S)는 늘 두 시즌이라 코드가 채운다. Spring에 돌려주는 결과(코드값·칸)는 그대로다. 도구 경로는 도구 인자가 코드값이라 코드 목록(`code_values_text`, 디테일 포함)을 그대로 쓴다. 첫 질문 약 6,070 → 3,900토큰(코드 목록 2,644 → 1,137, 출력 스키마 1,003 → 459), 이어 묻기 약 6,740 → 4,630. 15문항 회귀(2회씩)에서 480필드 중 478 일치 — 다른 2개는 "와이드 팬츠 유행해?"의 묻는 축(전에도 실행마다 달랐다 → 늘 없음)과 이어 묻기 다시 쓴 질문의 어미. enum을 뺀 뒤 묻는 축을 ITEM_TYPE으로 채우는 경향이 있어 "축을 콕 집어 묻지 않으면 빈 값" 경우를 규칙에 적었다.
  - 카테고리·종류는 **공통코드 목록의 이름**에서만 고른다(카테고리 이름 옆에 속성의 일상 표현을 힌트로 준다). 종류를 골랐으면 그 종류의 카테고리를 따른다. Spring은 공통코드에 없는 값을 버린다(나머지 해석은 쓴다).
  - 기간은 날짜가 바르고 from ≤ to ≤ 오늘일 때만 쓴다.
  - **속성 조건(`materials`·`colors`·`silhouettes`·`genders`·`patterns`·`details`)**: 대상을 좁히는 소재·컬러·실루엣·대상 라인·패턴·디테일 값("체크 셔츠" → 셔츠 + CHECK, "하프넥 니트" → 니트 + NECK_HALF) — "와이드 팬츠" → 하의 + WIDE, "크롭 아우터" → 아우터 + CROPPED, "블랙 레더 재킷" → 레더 재킷 + BLACK, "여성 아우터" → 아우터 + WOMEN(라인 값이 없는 분석 결과는 걸리지 않는다). 질문 단어(글자 비교)로 넘기면 "와이드 데님 팬츠"·"와이드 슬랙스"가 빠지므로 코드 값으로 거른다. 묻는 축의 값("유행하는 핏은?"의 실루엣)·종류 이름에 든 소재(데님 팬츠)는 넣지 않는다. 대상이 둘 이상이라 한 범위로 못 담으면("레더 재킷이랑 와이드 팬츠") 조건은 비우고 대상마다 질문 단어로 넘긴다(도구 경로는 대상마다 따로 센다).
  - **묻는 축(`focus`)**: 유행 질문이 주로 묻는 축 — 핏 → SILHOUETTE, 소재 → MATERIAL, 컬러 → COLOR, 패턴·무늬 → PATTERN, 디테일·포인트 → DETAIL, 아이템 → ITEM_TYPE, 카테고리 비교 → CATEGORY. 집계는 그 축을 첫 축으로 둬 판단 근거의 막대와 예시 원문이 그 축의 상위 값으로 나온다. 범위에서 빠진 축(종류를 콕 집었는데 ITEM_TYPE)이면 무시한다.
  - **증감(`change`)**(사용자 요청): 유행 질문이 직전보다 늘었는지·줄었는지를 물으면 UP(급상승·늘어난)·DOWN(줄어든·식은)·BOTH(변화·전월 대비)를 고른다. "뜨는·유행하는"처럼 비교 말이 없으면 비운다. "전월 대비·전주 대비"는 기간이 아니라서 비교 기간은 기본(최근 4주 vs 직전 4주)이다.
  - **"요즘 ~ 특징은?"은 유행 질문이다**(사용자 결정): 지금 많이 입는 그 옷이 어떤지라서 집계로 답한다(묻는 축은 비운다). 검색으로 보내면 "요즘·특징" 같은 일반 말 때문에 유사도가 기준 0.60 아래로 떨어져 근거 없음이 됐다. 지금을 가리키는 말이 없는 정의·코디 질문은 검색이다.
  - **시즌(`seasons`)**: F/W·올가을 같은 시즌 표현을 시즌 코드로도 돌려준다(Spring이 공통코드 `TREND_SEASON`을 보낸다). 기간(최근 6개월)만으로는 다른 시즌 자료가 섞이기 때문이다. 해석이 기간을 빠뜨려도 시즌이 있으면 집계는 시즌 기간(6개월)으로 센다. 규칙 해석·검색 경로는 시즌으로 거르지 않는다(Chroma 메타에 시즌이 없다).
  - **질문 단어(`terms`)**: 카테고리·종류·속성 코드로 옮기지 못한 패션 단어(무스탕·발마칸 코트·고프코어…, 최대 3개). 버리면 "무스탕 유행해?"가 "아우터 유행"으로 넓어진다. 종류로 그대로 옮긴 말(패딩)·카테고리 말·일반어·속성 값 이름은 넣지 않는다. AI 서비스와 Spring이 빈 값·20자 넘는 값·중복을 거른다. 규칙 해석은 비어 있다.
  - 패션이 아니면(`fashion=false`) 집계·검색·답변 없이 안내 한 줄(`OFF_TOPIC`)만 돌려준다. 애매하면 패션으로 본다(날씨·면접 옷차림, 신발·가방도 패션).
  - **패션잡화(신발·가방·모자·액세서리·주얼리)·뷰티 질문은 유행 집계로 보내지 않는다**(trend=false·카테고리 없음). 의류 원문만 세므로, 세면 옷으로 답한다. 검색으로 가서 기준 유사도가 근거 없음으로 막는다.
- **이어 묻기**: 화면이 최근 질문·해석 **3건**(`history`, 질문은 해석이 다시 쓴 것)을 같이 보낸다. 해석이 이어 묻기면 생략된 대상·기간을 바로 앞 해석에서 채워 **혼자서도 뜻이 통하는 질문으로 다시 쓰고**(`question`), Spring은 **검색·답변·도구 경로에 다시 쓴 질문**을 쓴다 — "그럼 하의는?"을 그대로 임베딩하면 엉뚱한 근거가 뽑힌다.
  - **유행 질문인지(trend)는 이어받지 않고 지금 질문으로 다시 정한다.** "요즘 유행하는 아우터는?" 뒤의 "그건 어떻게 입어?"는 코디 질문이다. 묻는 말이 빠진 질문("그럼 하의는?", "지난달은?")만 앞 질문과 같은 것을 묻는 것으로 본다.
  - 화면에는 사용자가 쓴 질문을 두고 답 위에 "이렇게 이해했어요 · 요즘 유행하는 하의는?"을 보인다. 범위 밖·오류 질문은 앞 대화에 넣지 않는다.
  - 화면이 보낸 값이라 Spring이 건수(최근 3)·길이(500자)·공통코드에 없는 값·잘못된 날짜를 거르고, AI 서비스도 3건만 받는다. 많이 넣을수록 엉뚱한 앞 질문에 이어 붙인다.
- **규칙 해석**(AI 실패 때 대체, `QuestionInterpreter`): 유행 단어 = 공통코드 `RAG_TREND_WORD` 코드명, 카테고리 = `TREND_CATEGORY` 이름·속성(재킷·바지…), 종류 = `TREND_ITEM` 이름과 괄호 안 표기(긴 이름이 이김, 기타 종류는 제외). 기간: 지난주·이번 주·지난달·이번 달·최근 N일/주/개월·올해·작년, 시즌 표현(올가을·26FW)은 최근 6개월. "전월 대비"는 비교 표현이라 기간이 아니다.
  - **알려진 한계**: 주제(패션인지)와 이어 묻기를 모른다. "요즘 유행하는 운동화는?"도 "유행" 때문에 유행 집계(범위 전체)로 간다. 검색 질문은 기준 유사도가 따로 막는다.
- 해석 결과는 답 말풍선 머리(근거 배지 옆)에 보인다("유행 질문 — 원문 수로 판단 · 아우터 · AI 해석"). "규칙 해석"이 보이면 AI 해석이 실패한 것이다 — Spring 로그 `질문 해석(AI) 실패`, AI 로그에 `POST /interpret 422`면 Claude 호출 전 요청 형식에서 막힌 것이다(빈 값은 null이 아니라 ""로 보낸다).

## 유행 질문 — 도구 경로

- **유행 질문은 모두 도구 경로로 답한다**(2026-10-29 사용자 결정). **Claude는 무엇을 셀지 고르고, 숫자는 집계 코드가 센다.**
- **해석 범위는 Spring이 미리 센다**: 해석 범위의 집계(축별 상위 10개 + 예시 원문)를 첫 메시지 `<prefetched>`에 넣는다. 순위·제외·특징 질문은 Claude 호출 한 번(final_answer)으로 끝나고, 비교·추이처럼 다른 범위·기간이 필요할 때만 도구를 더 부른다. 미리 센 집계로만 답하면 판단 근거 상자는 이 집계(막대는 상위 5개).
- **속도·비용**: 도구 경로 호출은 effort medium(기본값이면 길게 생각해 한 단계가 40초를 넘었다). 규칙·도구 정의(약 8,000토큰)는 둘째 단계부터 캐시해 셋째 단계부터 싸게 읽는다 — 한 단계로 끝나는 질문에는 캐시를 만들지 않는다(만드는 값 1.25배만 든다). AI 서비스 `/agent/step`은 Claude를 한 번 부르고 응답 블록을 돌려줄 뿐이고, 반복·도구 실행은 Spring `AgentService`가 한다(집계 데이터가 Spring DB에 있다). 규칙은 `ai/prompts/rag/agent.md` + `answer.md`의 system·system_trend + 허용 코드 목록.
- 도구: `count_trend`(범위·기간·시즌·축·증감·top → `TrendFactsService.count`의 집계 줄 + 예시 원문 6건. 축별 상위 `top`개, 기본 10·최대 15 — 제외·다음 순위 질문도 다시 부르지 않고 답한다), `trend_series`(값 최대 5개(`values`)의 주별 원문 수와 그 주 전체 분석 원문 수(한 줄), 2~26주 → `TrendFactsService.series` — 12주·값 하나일 때는 "최근 3개월"을 덮지 못하고 상위 5개 추이에 호출 상한을 다 썼다, 진단 B3), `search_documents`(질문과 비슷한 원문 → AI `/search`, 카테고리로 좁힐 수 있다), `final_answer`(답 — 형식은 `/answer`와 같다: summary + points 또는 body).
- **추이 차트는 서버가 만든다**(2026-10-29 진단 E1): 도구 경로가 `trend_series`를 부르면 마지막 결과로 꺾은선 차트(`RagAnswerView.chart`, 화면 `line-chart.js`)를 붙인다. 값은 **그 주 전체 분석 원문 중 비중(%)** — 건수로 그리면 수집량이 늘어난 주에 모든 선이 함께 오른다. 주별 전체 원문 수는 차트 아래 한 줄. Claude는 차트 숫자를 쓰지 않는다(표 수치는 여전히 Claude가 옮긴 글 — 수치 대조로 경고만).
- **이유·배경·사례는 문서 검색 도구로 근거를 찾는다**(2026-10-29 진단 B2): 집계는 무엇이 많은지만 알려 줘 "와이드 팬츠가 유행하는 이유는?"에 근거 글이 없었다. `search_documents`는 기준 유사도(`rag.min-score`) 이상·분석 완료 원문만, 문서마다 가장 앞선 청크 하나(300자 — 결과 순서는 하이브리드 순서)로 최대 4건을 [n]과 함께 준다 — 집계 예시와 같은 번호 체계라 같은 원문은 같은 번호. 검색 결과의 건수는 유행 근거로 쓰지 않는다(`agent.md`). AI 서비스 호출이 실패하면 도구 결과로 알리고 집계로만 답한다.
- 도구 입력 코드는 사용 중 공통코드로 검증하고, 틀리면 "입력 오류"를 돌려줘 다시 부르게 한다. 모델은 `rag.agent.model`(기본 `claude.model` = Sonnet), 도구 호출 상한 `rag.agent.max-tool-calls`(기본 6, 사용자 결정) — 넘으면 지금까지 결과로 답하라고 알린다. Claude 호출 8단계·90초 안.
- 근거 번호 [n]은 도구 결과의 예시 원문에 Spring이 붙인다 — 답은 그 번호만 인용할 수 있고, 없는 번호는 지운다(출처 정리는 고정 경로와 같은 `view`). 화면의 해석 표시는 "도구 조회".
- **판단 근거 상자는 답이 인용한 집계다**(`AgentService.usedFacts`, 2026-10-29 진단): Claude가 직접 부른 count_trend 중 답이 인용한 예시 원문이 나온 것을 부른 순서로(같은 범위·기간은 한 번, 최대 3개 — 첫 것이 주 상자, 나머지는 `moreFacts`로 상자마다 기간을 붙인다). 없으면 미리 센 집계. 첫 집계만 그렸을 때는 비교 질문("레더 재킷이랑 무스탕")에 해석 범위("전체") 막대가 나와 답과 어긋났다.
- **실패한 도구 경로의 토큰도 센다**: 도구 경로가 실패해 고정 경로로 답하면 두 경로 토큰을 합쳐 질문 로그에 남긴다(실패해도 과금된다).
- 실패하면(final_answer 없이 끝남·시간 초과·AI 오류·응답 처리 오류) **고정 경로**로 답한다 — 해석 범위를 한 번 세어(축별 상위 5개) 그 집계와 예시 원문으로 `/answer`가 답한다. `rag.agent.enabled=false`면 늘 고정 경로다.

## 유행 집계 (`TrendFactsService` — 두 경로가 같이 쓴다)

- **센다**(`TrendFactsService`, 질문할 때 바로 — 주간 배치를 기다리지 않는다): 분석 완료 원문 중 기간 안·범위(카테고리·종류) 안의 것을, 아이템 종류·카테고리(범위가 없을 때)·소재·컬러·실루엣별로 **원문 수**(한 원문에 여러 번 나와도 1)와 **출처 수**(서로 다른 출처 — 아래), 직전 같은 길이 기간의 원문 수로 센다. 축마다 상위 5개(도구 경로는 `top`).
- **출처 수**(API 필드명은 `mediaCount`): 대중화는 여러 곳에서 보이는 것이다. 한 매체가 같은 옷을 여러 번 올린 것과 가르기 위해 같이 센다. **유행점수와 같은 출처 기준**(`TrendFactsService.sourceKey` — 매체명, 직접 업로드·직접 등록·매체 미입력은 원문마다 다른 출처)으로 센다(2026-10-29 진단). 매체명 그대로 셌을 때는 직접 업로드가 모두 한 곳이 되어 "유행점수는 높은데 1개 매체"로 판단 근거와 답이 어긋났다. 같은 원문이 다시 들어온 것은 저장 단계에서 URL로 막는다([`document-upload.md`](document-upload.md)). 출처가 한 곳뿐이면 Claude가 "대중화 여부는 더 봐야 한다"고 밝힌다.
- **기간**: 질문이 정한 기간, 없으면 오늘까지 4주. 그 안에 원문이 없으면 범위 원문 중 가장 최근 게시일까지 4주로 옮기고(8주 넘게 오래됐으면 stale — 노란 안내), 기간을 정한 질문은 옮기지 않고 근거 없음.
- **기타 값은 아이템명 상위를 같이 센다**: 카테고리 `ETC`·종류 `…_ETC`는 목록에 없는 옷이 한데 모인 것이라 "기타 아우터 7건"만으로는 무엇이 뜨는지 모른다. 그 안의 아이템명(공백만 정리, 표기 흔들림은 그대로)을 원문 수로 세어 상위 3개를 집계 줄에 괄호로 붙이고, 화면은 막대 아래 한 줄로 보인다. Claude는 기타 묶음을 순위 항목으로 쓰지 않고 아이템명으로 무엇이 섞였는지만 쓴다.
  - **종류 추가 기준**: 기타 묶음 안의 같은 아이템명이 기본 집계 기간(4주)에 **원문 3건 이상**이면 공통코드에 아이템 종류로 추가할지 사용자와 검토한다(1~2건은 답변 규칙에서도 "사례가 적다"로 보는 수다). 후보 자동 탐지·기타만 재분류는 크롤링 뒤 검토.
- **속성 조건으로 거른다**: 범위(카테고리·종류)에 더해 그 값을 가진 의류 아이템만 센다 — 종류 안에서는 하나라도(OR), 종류끼리는 모두(AND). 대상 이름 뒤에 " · 와이드"처럼 붙는다. 조건 축 값이 아예 없는 원문(라인은 최근 분석부터 생겼다)은 거를 수 없어 빠지므로, 빠진 원문이 있으면 `[조건 정보] 범위 원문 N건 중 라인 값이 있는 원문 M건만…` 줄을 넣고 Claude가 "값이 있는 원문 M건 기준"을 밝힌다(2026-10-29 진단 C4).
- **시즌을 정하면 원문의 시즌 값으로 거른다**: 정형 결과 `seasons`가 그 시즌인 원문만 센다(시즌 값이 없는 원문은 빠진다). 대상 이름 뒤에 " · 가을·겨울 시즌"이 붙는다.
- **기간·시즌을 모두 정하지 않은 질문은 지금 시즌으로 센다**(2026-10-30 사용자 결정): "요즘 유행하는 하의는?"의 최근 4주에는 다음 시즌 런웨이 기사(10월이면 S/S)가 섞여 반바지가 뜰 수 있다. 기간은 최근 4주 그대로 두고 지금 시즌(`TrendFactsService.currentSeasons`) 원문만 센다. 해석(AI·규칙)과 상관없이 집계가 정하므로 고정 경로·도구 경로(`count_trend`에 기간·시즌이 없을 때)에 모두 걸린다. 추이(`trend_series`)는 거르지 않는다.
  - **지금 시즌 = 그달의 계절 + 계절 마지막 달이면 다음 계절**(3~5 봄·6~8 여름·9~11 가을·12~2 겨울. 10월 → 가을, 11월 → 가을·겨울). 반기(S/S·F/W)로 나누면 7월에 여름 옷이, 1월에 겨울 옷이 빠지고, 다음 계절을 늘 넣으면 12월에 S/S 런웨이 기사(봄·여름)가 섞인다.
  - 지금 시즌 원문이 `MIN_SEASON_DOCS`(5)건보다 적으면(시즌 값이 없는 예전 분석도 빠진다) 시즌 구분 없이 센 것을 쓴다. 어느 쪽인지 `[시즌]` 줄(조건 정보와 같은 자리)로 Claude에게 알리고, Claude는 summary 기간에 "최근 4주 · 가을 시즌"처럼 밝힌다. 화면은 대상 이름의 " · 가을 시즌"으로 보인다.
  - 범위 원문이 0건이라 가장 최근 자료 4주로 옮길 때는 시즌으로 거르지 않는다(그때의 시즌이 지금과 다르다).
- **소재·컬러·실루엣 값마다 아이템 종류를 같이 센다**(교차): 같은 의류 아이템 기준으로 그 값으로 나온 종류 상위 3개(이름의 괄호 힌트는 뗀다). 집계 줄에 "[주요 아이템: 레더 재킷 3건, …]"로 붙고 답 본문에서 쓰인다. "컬러별 활용 아이템"의 근거이고, Claude는 이 짝에 없는 아이템을 추천으로 지어 넣지 않는다. 종류를 콕 집은 질문은 세지 않는다.
- **질문 단어는 키워드·아이템명에서 센다**: 그 말이 들어간(공백·대소문자 무시) 원문 수·출처 수·직전 기간 원문 수와 실제로 나온 표현 상위 3개. **범위(카테고리)와 상관없이** 센다(키워드는 문서 단위라 범위에 묶기 어렵다). **옷 개수가 아니라 언급 수**다 — "무스탕 칼라"(깃만 무스탕인 레더 재킷)도 걸리므로 나온 표현을 같이 보여 Claude가 구분해 말하게 한다. 그 단어가 나온 최근 원문(단어마다 3건)을 예시 원문 앞에 둔다.
  - **여러 낱말은 낱말이 모두 들어 있으면 걸린다**: "와이드 팬츠" → "와이드 데님 팬츠"·"와이드팬츠"도 센다.
  - **대상 옷의 포인트**: 건수만으로는 어떤 옷이 뜨는지 알 수 없어서, 아이템명에 그 말이 들어간 옷(대상 옷)의 **컬러·소재·실루엣 상위 3개(원문 수, 직전 대비)**, 같은 원문에 **함께 나온 옷 종류**(매치), 그 원문들의 **다른 키워드**(스타일)를 센다. 키워드에만 나온 원문은 대상 옷을 몰라 포인트에서 빠진다. 화면은 같은 이름("레더 재킷: …")으로 시작하는 줄이 둘 이상이면 이름을 소제목으로 묶는다.
- **예시 원문**: 첫 축 상위 3개 값마다 최근 원문 2건. 첫 축은 아이템 종류이고, 종류 값이 하나도 없으면(종류 없는 분석 결과) 카테고리다. 종류를 콕 집은 질문은 묻는 축이 있으면 그 축 상위 값마다 최근 원문 2건, 특징 질문(묻는 축 없음)·감소 질문은 **대표 원문** 6건 — 범위 원문을 축별 상위 3개 값을 몇 개 가졌는지 순(같으면 최신 순)으로 고른다(2026-10-29 사용자 지적: 최근 6건을 그대로 쓰면 답의 공통 특징과 상관없는 원문이 근거로 붙었다). AI 서비스가 Chroma에서 doc_id로 꺼내 출처로 쓴다(유사도 없음 — 화면 "집계 예시").
- 기간 안에 범위 원문이 없으면 **AI를 부르지 않고** 근거 없음("○○(기간)에 아우터 원문이 없습니다").
- **Claude에게 보내는 집계**(`Facts.lines`): 묻는 축이 정해진 질문은 그 축(첫 축)만 보내고, 묻는 축이 없는 질문(특징·브리프 등)은 모든 축을 보낸다. 질문 단어·대상 옷 포인트 줄은 함께 보낸다.
- **특징 질문은 공통 조합·키워드도 센다**(2026-10-29 사용자 지적 — 축마다 따로 센 1위를 이어 붙이면 "그레이·오버사이즈·케이블 니트"가 실제로 있는 옷인지 알 수 없다): 묻는 축·증감이 없는 유행 질문이면 `[공통 조합]`(같은 옷에서 함께 나온 서로 다른 축 값 두 개 — 아이템 종류·컬러·소재·패턴·실루엣·디테일, 원문 수 상위 5개)과 `[키워드]`(범위 원문의 키워드 상위 8개) 줄을 보낸다. 둘 다 **원문 2건 이상**만(1건은 우연한 조합). 기타 묶음 값은 조합에서 빼고, 범위 이름에 든 키워드("니트")도 뺀다. 키워드는 공백만 정리한 표기라 "오버핏"·"오버사이즈 핏"은 따로 센다. Claude는 가장 흔한 조합으로 대표 모습을 먼저 쓰고 축별 상위 값·키워드로 뒷받침한다(`answer.md`).
- **유행 판단은 유행점수로 한다**(`TrendFactsService.trendScore`, 사용자 결정): 유행점수 = 출처 수 + 0.5 × (원문 수 − 출처 수) — 출처마다 첫 원문 1점, 같은 출처의 반복 원문 0.5점. 한 매체가 10번 올린 것(5.5)보다 5곳이 2번씩 다룬 것(7.5)이 높다. 출처는 매체명이고, 직접 업로드(이미지 — 인스타 게시물로 간주)·매체 미입력 원문은 출처를 몰라 원문마다 다른 출처로 본다. 축마다 값을 유행점수 순으로 골라 집계 줄에 "유행점수 N"을 붙인다. 판단 근거 막대 길이도 유행점수다(증감 질문은 건수). 반복 가중치 0.5는 제안값이다.
- **증감률은 서버가 계산한다**(`TrendFactsService.rate`, 사용자 요청): 집계 줄의 값·질문 단어·포인트마다 "직전 N건(+200%)"을 붙인다(직전 0건 "신규"). Claude가 나누지 않게 완성된 값을 준다. 증감 질문이면 축마다 유행점수 순 대신 **비중 변화(%p) 순**으로 고른다 — UP은 비중이 늘어난 값만, DOWN은 줄어든 값만(이번 기간 0건 포함), BOTH는 달라진 값. 직전 범위 원문이 0건이면 비중을 비교할 수 없어 원문 수 차이로 고른다. **이번·직전 모두 1건 이하인 값은 증감 순위에서 뺀다**(`MIN_CHANGE_DOCS` 2, 2026-10-29 진단 C3 — 0→1 "신규"가 급상승으로 답에 끼었다). "[정렬]" 줄로 Claude에게 알린다. 상위 값에 이번 기간 원문이 없으면(감소) 범위의 최근 원문을 예시로 준다.
- **수집량 보정**(2026-10-29 진단 C2): 값마다 **비중**(그 기간 범위 원문 중 그 값이 나온 원문 %)과 직전 비중·변화(%p)를 집계 줄에 붙인다("· 비중 60%(직전 33%, +27%p)"). 원문 수 증감률만 보면 수집량이 늘 때 모든 값이 "급상승"이 됐다(실측: 직전 17건 → 이번 129건이라 +900%~+5000%). 범위 원문 수가 직전 대비 1.5배 이상·2/3 이하로 달라지거나 직전이 10건 미만이면 `[수집량 주의]` 줄을 넣고(`TrendFactsService.volumeNote`) Claude는 비중 변화로 판단하며 자료량 차이를 한 줄로 밝힌다. 기준값(1.5배·10건)은 제안값이다.
- **판단 근거 상자**(답 아래): 범위·기간·원문 수·출처 수와 **묻는 축(첫 축) 막대**만 그린다(도구 경로가 집계 여럿을 인용했으면 상자 여럿). 질문 단어가 있으면 그 말의 언급 원문 수 막대를 먼저 그리고, 범위가 "전체"면 축 막대는 뺀다 — "레더 재킷이랑 무스탕" 답 아래에 전체 아이템 순위가 나와 답과 어긋났다(2026-10-29 진단 B1). 나머지 축·질문 단어·대상 옷 포인트는 답 본문과 겹쳐 그리지 않는다(API 응답 `facts`에는 있다). 막대 오른쪽은 건수와 직전 대비 증감(▲·▼, 직전 0건이면 NEW)만 쓰고 출처가 한 곳이면 "· 1개 출처"를 붙인다. 증감 질문이면 ▲·▼ 옆에 비중 변화(%p)와 "33→60%"(직전→이번 비중)를 쓰고 막대 길이도 비중 변화 폭이다(직전 원문이 없으면 증감률·건수). 수집량 주의가 있으면 상자 머리 아래에 한 줄 보인다. 전체 수치(건수·출처·직전·증감률·비중)는 막대에 마우스를 올리면 보인다.
- 아이템 종류가 없는 분석 결과는 종류 집계에 안 잡힌다 — 재분석해야 한다.

## 검색 질문 — 근거 검색

- **근거 기준**: 리랭킹을 켜면 리랭커 점수(공통코드 `RAG_SEARCH.RERANK` 속성, 기본 0.10), 끄면 유사도(1 − 코사인 거리, `rag.min-score` 기본 0.60) 이상인 청크만 근거. 없으면 Claude를 부르지 않는다(`NO_EVIDENCE`). 근거가 질문에 맞지 않으면 `MODEL_DECLINED`.
- **리랭킹**(2026-10-30 사용자 결정 — 속도보다 정확도): 하이브리드 후보 30개를 리랭커(`RERANK_MODEL`, 기본 `BAAI/bge-reranker-v2-m3`)가 질문과 함께 읽어 0~1 점수(`rerank`)를 매기고, **순서와 근거 기준을 모두 그 점수로** 바꾼다. 유사도는 관련·무관이 0.52~0.69에서 겹쳐(청크 하나에 아이템 여럿이 섞여 희석된다) 기준 하나로 가르지 못했다.
  - **켜기/끄기는 관리 > 공통코드 `RAG_SEARCH`의 `RERANK` 사용 여부**, 리랭커 기준은 그 속성(0~1 — 아니면 기본값과 경고 로그). 질문마다 읽어 재기동 없이 다음 질문부터 바뀐다(사용자 결정 — 관리 화면에서). 두 점수는 척도가 달라 방식마다 기준을 따로 둔다 — 켜고 끌 때 기준을 같이 바꿀 일은 없다.
  - Spring이 요청마다 AI 서비스에 리랭킹 여부를 넘긴다(`/answer`의 `rerank`, `/search?rerank=`). 도구 경로의 `search_documents`도 같은 설정·기준을 쓴다. 화면은 리랭킹 답이면 "관련도", 아니면 "유사도"로 적는다(`reranked`).
  - 리랭커 모델은 AI 서비스 기동 때 미리 올려 상주한다(bge 약 2.3GB, `PRELOAD_MODELS` — [`ai-development.md`](../ai/ai-development.md)). 미리 올리기를 끄면 첫 리랭킹 때 올리고, 리랭킹을 끈 채로 쓰면 올리지 않는다. **이 PC(CPU)에서 후보 30개에 20~30초**(최대 50초) 더 걸린다 — GPU면 1초 미만으로 본다(추정).
  - **2026-10-30 `rerank_eval`**(같은 하이브리드 후보 30개): 리랭커 Recall@8 0.755 · Precision@8 0.945 · MRR 1.000(유사도 순서 0.648 · 0.842 · 0.900). 자료 없는 주제 1위 최고 0.042, 정답 있는 질문은 모두 정답 문서가 0.10 이상(블레이저 출근룩 0.145가 최저) — 그래서 기준 0.10. 약점: 아이템이 룩의 일부인 원문은 낮게 매긴다("스커트 코디"의 정답 16건 중 0.10 이상은 2건). Qwen3-Reranker-0.6B도 견주려 했으나 이 PC(CPU)에서 같은 평가가 1시간 넘게 끝나지 않아 중단하고 bge로 정했다 — GPU 서버로 옮기면 다시 견줄 만하다.
- **하이브리드 검색**(2026-10-30 사용자 결정, `HYBRID_SEARCH` 기본 켬): 벡터 상위 N개와 키워드(BM25) 상위 N개를 **RRF**(`1/(60+순위)`)로 합쳐 순서를 정한다. 벡터가 놓치는 드문 고유한 말("블레이저"·"체크 셔츠")을 글자 그대로 잡기 위해서다.
  - **키워드는 후보를 넓히고 순서만 바꾼다 — 근거 기준은 그대로다.** 키워드로만 걸린 청크도 같은 질의 벡터로 유사도를 구해 `score`(유사도)는 언제나 같은 뜻이고, 기준 유사도도 그 값에 건다. 키워드가 많이 맞았다고 기준 미달 청크가 근거가 되지 않는다. 순서(`fused`)는 `/search` 결과 순서·최신성 가중치·문서 번호에 쓴다.
  - 토큰은 공백·기호를 지운 **글자 2-gram**이다 — 형태소 분석기 없이 "와이드팬츠"·"와이드 팬츠"가 같게 잡힌다.
  - 키워드 색인은 AI 서비스 메모리에 Chroma 청크 글로 만들고(따로 저장하지 않는다), 색인을 넣거나 지우면 버렸다가 다음 검색 때 다시 만든다. **Chroma를 이 서비스만 고친다는 전제**다 — 서버형에서 다른 프로세스가 청크를 넣으면 재기동 전까지 키워드 쪽에 안 보인다.
  - 질의 임베딩은 한 번만 만든다(CPU에서 수 초). Chroma 내부 `_embed`를 쓰므로(`vector_store.embed_query`) Chroma 버전을 올리면 확인한다.
- 카테고리를 말했으면 그 카테고리 아이템이 있는 원문만 찾는다(청크 메타 `cat_<코드>: True` — Chroma는 목록·부분 일치 필터가 없다).
- 기간이 없으면("요즘" 포함) 자르지 않는다: 후보 30개 → 기준 이상만 → **관련 점수(리랭커·RRF·유사도) × 0.5^(경과일/28)**(반감기 4주)로 다시 순위 → 상위 `rag.top-k`(8). 가장 최근 근거도 8주가 넘으면 stale. 기간을 정했으면 그 게시일 범위로 자른다(메타 `published_num` 20261022).
- 검색 질문에는 집계 수치를 보내지 않는다 — 근거는 원문뿐이다.
- **기준 유사도 0.60**(리랭킹을 껐을 때): 관련 있는 질문의 1위 근거와 데이터에 없는 주제의 1위 사이로 정한 값이다. 값은 사용자와 정한다. 아래 중 하나면 `py ai/evals/search_eval.py`(또는 AI `GET /search?q=`)로 다시 재고 사용자와 값을 다시 정한다.
  - 분석 완료 원문이 직전 측정 때보다 50건 이상 늘었거나 텍스트 원문이 새로 들어왔을 때(분포가 바뀐다).
  - 근거 없음이 잦다: 검색 평가 세트에서 정답 문서가 있는 질문 중 1위 유사도가 0.60 미만인 질문이 10% 이상.
  - 엉뚱한 근거가 잡힌다: 자료 없는 주제 질문의 1위 유사도가 하나라도 0.60 이상.
  - **2026-10-30 재측정**(분석 완료 152건, 텍스트 포함): Recall@8 0.648 · Precision@8 0.842 · MRR 0.899. 정답 문서 중앙 0.651, 정답 밖 상위 중앙 0.613, 자료 없는 주제 1위 최고 0.625("비키니 수영복" — 기준 이상 1건). 기준을 0.63으로 올리면 무관 주제는 막지만 정답 질문 16개 중 2개(스커트 코디 0.601·블레이저 출근룩 0.615)가 근거 없음이 되고(12.5% — 위 10% 조건) 정답 문서도 77%→61%만 남아 **0.60을 유지**했다. 무관 주제가 걸려도 답변 규칙이 근거가 맞지 않으면 `MODEL_DECLINED`로 막는다. 최신성 가중치(반감기 4주)는 이 측정(순수 유사도)으로 바꿀 근거가 없어 그대로 둔다.
  - **2026-10-30 하이브리드 비교**(같은 데이터): 벡터만 Recall@8 0.648 · Precision@8 0.842 · MRR 0.899 → 하이브리드 0.729 · 0.936 · 0.969. 블레이저 출근룩(R 0.00→0.40)·체크 셔츠 코디(0.50→0.83)·카고 팬츠(0.71→1.00)가 크게 좋아졌고 나빠진 질문은 없다. 자료 없는 주제 1위 유사도는 그대로다(키워드가 기준을 낮추지 않는다). 그래서 기본을 켬으로 했다.
- 예전 청크의 메타(`published_num`·`cat_*`, `meta_v` 2)는 AI 서비스 기동 때 채운다(다시 임베딩하지 않는다).

## 규칙

- **답의 줄에는 근거 원문 번호를 붙인다**(`answer.md`). 코드는 인용 번호가 하나도 없으면 답을 버린다(`MODEL_DECLINED`). 번호 없이 둘 수 있는 줄은 한계·주의 문장뿐이다.
- 근거는 **문서 단위로 묶어** 번호를 붙인다(출처 하나 = 문서 하나). 답은 결론 한 줄(`summary`) + 글머리 줄(`points`, 줄마다 `sources`) — 형식은 스키마(`answer.build_schema`)가, 줄 개수는 `answer.md`가 정한다(스키마에는 개수 제한이 없다).
- **인용한 출처가 모두 빠진 줄은 답에서 뺀다**(`RagService.points`·`body`, `answer._answer_from`): 지어낸 번호나 삭제·재분석 중인 문서만 인용한 줄은 확인할 수 없어서다. 본문(body)도 줄(문단·목록 줄·표 행) 단위로 같다. 일부만 빠졌으면 빠진 번호만 지운다. 처음부터 인용이 없는 줄(한계·주의 문장·표 머리)은 둔다. 출처가 하나도 안 남으면 `SOURCE_MISSING`.
  - **앞 단계는 번호를 지우지 않고 넘긴다**(2026-10-29 진단 F2): AI 서비스·AgentService가 없는 번호를 먼저 지웠을 때는 "인용 없는 한계 문장"과 구분이 사라져 지어낸 줄이 출처 없이 남았다. AI 서비스는 없는 번호만 단 줄을 직접 빼고, AgentService는 그대로 넘겨 Spring이 뺀다.
- **답의 수치를 집계와 대조한다**(`AnswerNumbers`, 2026-10-29 진단 F1): 유행 질문(도구·고정 경로) 답의 N건·N곳·N%·유행점수 N 중 Claude가 읽은 집계 글(도구 결과·집계 줄)에 없는 것을 `unverifiedNumbers`로 돌려주고 경고 로그(`답의 수치 중 집계에 없는 것`)를 남긴다. 화면은 답 아래에 "집계에서 확인되지 않은 수치" 안내를 보인다. 답은 막지 않는다 — 단위 없는 표 칸 숫자·"2건 이하" 같은 기준 수치는 보지 않아 놓치는 것이 있다. 검색 답은 집계 수치를 쓰지 않아 대조하지 않는다.
- **답변 규칙은 경로별로 나눠 보낸다**: `answer.md`의 `system`(공통 — 답 모양·지어내지 않기·판매·단정·근거 부족) + 유행 질문(도구·고정 경로)은 `system_trend`, 검색 질문은 `system_search`.
- 이미지 근거는 사진 분석 요약이다("사진에서 보인다"). 질문은 500자까지. 답변은 글자로만 넣는다(HTML 해석 안 함).
- API는 **로그인만** 요구한다(홈은 프로그램이 아니다 — `@RequiresProgram`을 붙이지 않는다).
- **출처 열기**: 링크가 있는 원문은 새 탭, **이미지만 있는 원문**은 오른쪽 슬라이드 패널(사진 + 근거 청크 전체). 청크는 색인 형식(요약 줄·`키워드:`·`시즌:`·`아이템:` 줄, `indexer.summary_chunk`)을 나눠 분석 요약·아이템 카드(종류·카테고리, 소재·컬러·실루엣)·키워드·시즌 칩으로 보인다. 아이템명은 보이지 않고, 형식이 다른 청크는 글 그대로 둔다 — 색인 형식을 바꾸면 `home.html`의 `renderChunk`·`parseItem`도 고친다. 패널 사진 `GET /api/rag/sources/{docId}/image`는 로그인만 필요하고 **분석이 끝난 이미지 원문만** 열린다.
- 화면: 기다리는 동안 말풍선 안에 점 세 개(`silent` fetch — 전체 화면 스피너 없음), 오류도 말풍선(다시 묻기). 출처 행 id는 말풍선마다 따로(`ragSource-<답 번호>-<n>`) — 여러 답의 [1]이 서로 다른 출처를 가리킨다.
- **AI 호출 실패는 화면에 일반 안내만 보인다**(502, `ApiExceptionAdvice`): 다시 해 볼 만한 실패는 "잠시 후 다시 시도", 아니면 "관리자에게 문의". 실제 사유(AI 서비스 주소·`start-ai.cmd`·설정 키 이름)는 서버 정보라 화면에 내지 않고 서버 로그 `AI 서비스 호출 실패`에만 남긴다.
- **빈 본문**: 모델이 body에 따옴표만(`""`) 넣기도 해서 Spring(`RagService.blankBody`)이 따옴표·공백뿐인 본문을 비운다.
- **AI 서비스와 날짜는 문자열(`"2026-10-22"`)로 주고받는다.** RestClient 기본 JSON은 `LocalDate`를 배열로 써서 422가 난다. 실제 직렬화는 `AiClientWireTest`가 본다. 422면 사유에 필드(`loc`)가 남는다.
- 토큰·소요 시간은 Spring 로그(`질문 해석(AI)`, `도구 경로 답`, `RAG 질문`·`RAG 유행 질문 … 토큰`)와 AI 로그(`질문 해석`, `도구 경로 한 단계`, `RAG 답변 mode=`)에 남는다.

## 기획 브리프 — 챗봇 답 + PPT

- **챗봇에는 짧게, 브리프는 PPT로**(사용자 결정): 브리프 질문의 답은 시즌·범위와 핵심 방향 한 문장 + 핵심 트렌드 3~5개 + 시사점 한 줄. 표·축별 상위 목록·유행점수는 쓰지 않는다(`answer.md`).
- 판단 근거가 있는 유행 답에는 "📊 기획 브리프 PPT" 버튼이 붙는다. 누르면 `POST /api/rag/brief`(로그인만, Claude 한 번 — 30초~1분)가 질문을 다시 해석하고(묻는 축·증감은 비운다) **여러 갈래로 센다**(`BriefService`): 범위 전체 축(상위 10개, 컬러·소재·실루엣의 주요 아이템 포함), 카테고리별 아이템(범위가 없으면 아우터·상의·하의 상위 5개), 늘어난 값(축마다 5개), 출처 분포(`TrendFactsService.sourceMix` — 일반 사용자 이미지·매체별·직접 등록 텍스트), 예시 원문 8건.
- **Claude는 문장만 쓴다**(AI `/brief`, `prompts/rag/brief.md`, JSON 스키마 `app/rag/brief.py`): 8개 구성 — 기획 개요·핵심 요약(핵심 트렌드·주목할 변화·시사점) / 핵심 아이템 / 핵심 컬러(활용 아이템·배색) / 핏·실루엣·디테일 / 소재·패턴 / 데이터 근거 주의사항 / 상품 기획 제안(우선 검토·추천 조합·기본 vs 트렌드·테스트·불확실성) / 실행 과제. 유행점수는 쓰지 않고, 판매·재고·원가가 없으니 제안은 트렌드 관측 기반의 가설로 쓴다.
- **차트·건수는 서버 집계로 화면이 그린다**(Claude가 숫자를 만들지 않게): 카테고리별 아이템 막대, 컬러 칩(공통코드 컬러 이름 → RGB, `home.html` `COLOR_HEX`)과 비중(그 컬러가 나온 원문 ÷ 범위 원문), 실루엣·디테일·소재·패턴 막대, 출처 분포 막대. 기타 묶음은 차트에서 뺀다.
- PPT는 화면에서 만든다(`static/js/pptx-writer.js` — 외부 라이브러리 없이 zip-writer로 .pptx, 16:9 빈 레이아웃에 글상자·표·색 상자·사진). 슬라이드: 표지 / 1~8 구성 / 부록 레퍼런스(사진 출처 최대 8장 — 출처 주소에서 받아 JPEG로 바꿔 넣는다, 파워포인트가 webp를 못 읽을 수 있다).

## 질문 로그·피드백

- **질문마다 남긴다**(`RagLogService`, 테이블 `rag_query_logs`, 사용자 요청): 사용자·일시·질문·다시 쓴 질문·경로(AGENT 도구·TREND 고정 집계·SEARCH 검색·OFF_TOPIC)·근거 여부·사유·답 글(결론 + 글머리 또는 본문)·출처 원문 ID·토큰(해석 + 도구 경로 + 답변 — 실패한 도구 경로의 토큰도 넣는다)·도구 경로가 읽은 집계·검색 결과 글(`tool_results` — 👎 답의 수치를 나중에 대조, 관리 화면 상세 "읽은 집계")·소요 시간. 저장이 실패해도 답은 돌려준다.
- `POST /api/rag/ask` 응답에 `logId`가 붙고, 답 아래 👍👎가 `POST /api/rag/feedback`(질문한 사람만, 다시 누르면 지움)으로 남는다.
- **관리 화면 "챗봇 질문 로그"**(`rag-log`, 관리 그룹, 조회만): 기간·피드백·경로로 거르고 건수·👍👎·평균 시간·평균 입력 토큰을 보인다. 행을 누르면 질문·답 전체. 질문에 사내 기획 정보가 들어갈 수 있어 권한을 준 사람만 본다.
- **보관 180일**(`rag.log.retention-days`) — 매일 4시에 지난 로그를 지운다. 기간은 사용자와 다시 정할 수 있다.

## 성능

- 챗봇 집계는 질문마다 기간 안 원문을 읽어 메모리에서 센다. 원문 값은 100건씩 묶어 읽고(`TrendItem.values` `@BatchSize`), `source_documents(status, published_at)` 인덱스로 기간을 고른다.
- **집계가 1초를 넘으면** 경고 로그 `유행 집계가 느립니다`를 남긴다 — 그때 값 세기를 DB 집계 쿼리(GROUP BY)나 일별 집계 표로 옮긴다.

## 평가

- **대표 질문 세트** `ai/evals/rag_questions.json`: 상품기획·MD·디자이너 관점 질문과 기대 답 요건. 구조를 바꾸면 같은 세트로 전후를 비교한다.
  - 질문마다 필요한 조회(`needs`), 답에서 확인할 요건(`expect` + 공통 `common_expect`)을 둔다. 질문 문장은 사용자 말투 그대로 둔다. 요건 문구를 고치면 비교할 기준 결과도 같은 문구로 다시 채점한다.
- **집계 검증**(Claude 호출 없음): Spring 앱을 내리고 jar를 `--spring.profiles.active=local --server.port=0 --rag.facts-check.cases=ai/evals/facts_cases.json --rag.facts-check.out=ai/evals/results/facts-check.json`로 띄우면 `FactsCheckRunner`가 조건(해석 결과를 직접 줌)마다 판단 근거를 저장하고 끝난다. `py ai/evals/facts_check.py`가 같은 조건을 SQL로 다시 세어(같은 정렬 — 유행점수·증감) 맞댄다. `--docs F02 F15`처럼 조건 ID를 주면 값마다 SQL로 센 원문 목록(이번·직전 기간의 문서 ID·게시일·매체)도 찍는다 — 챗봇 답의 "N건"을 확인할 때는 답의 해석(범위·속성·시즌·기간·증감)을 `facts_cases.json`에 조건으로 넣고 돌린다. 화면에는 원문 목록을 두지 않는다(운영 데이터가 많아지면 비효율 — 사용자 결정). DB는 앱과 같은 H2 2.5.252·JDK 17로 읽는다 — 2.2.224로 열면 "File corrupted"로 보인다.
- **리랭커 검증**(Claude 호출 없음): `ai` 폴더에서 `.venv/Scripts/python evals/rerank_eval.py --model <모델>`이 검색 검증과 같은 질문으로 하이브리드 후보를 리랭커로 다시 매겨 순위 지표·점수 분포와 **기준값별 통과율**(정답 질문 중 정답이 하나라도 통과·자료 없는 주제 통과 수)을 유사도와 나란히 낸다. 후보는 `results/rerank-candidates.json`에 두고 모델끼리 같은 후보로 맞댄다(`--refresh`로 새로). 리랭커 기준을 다시 정할 때는 이 표로 사용자와 정한다.
- **검색 검증**(Claude 호출 없음): `py ai/evals/search_eval.py`(벡터만은 `--vector` — 하이브리드와 비교할 때 둘 다 돌린다)가 `search_questions.json`의 질문마다 AI 서비스 `/search`로 문서 순위(결과 순서)를 받아 Recall@8·Precision@8·MRR과 점수 분포(정답 문서·정답 밖 상위·자료 없는 주제 1위)를 낸다. 정답 문서는 분석 결과에 규칙(rule)을 적용해 정한다. 기준 유사도 재검토 조건은 위 검색 질문 절.
- **답변 평가**(실제 Claude 호출 — 비용이 든다): Spring 앱을 내리고(H2 파일 잠금) jar를 `--spring.profiles.active=local --rag.eval.questions=<질문 파일> --rag.eval.out=<답 파일>`로 띄우면 `RagEvalRunner`가 챗봇과 같은 처리(`RagService`)로 답을 받아 저장하고 끝난다. 이어 묻기(`followup_of`)는 앞 답을 앞 대화로 넣는다. 채점은 `py ai/evals/judge.py <답 파일>`(채점 모델이 답과 근거를 대조해 요건마다 pass·fail·na). 답 파일에는 도구 경로가 읽은 집계 글 전부(`toolResults` — 미리 센 집계·도구 결과)가 같이 남고, 채점은 그것과 자유 형식 본문(`body`)까지 본다 — 화면의 판단 근거(첫 집계 상위 5개)만 주면 도구로 더 센 수치를 "지어냈다"로 잘못 채점한다(2026-10-29 첫 실행에서 확인).
- 결과는 `ai/evals/results/`(커밋 제외 — 원문 요약이 들어 있다).

- `RagBodyTest`·`AnswerNumbersTest`: 본문 인용 정리(없는 번호만 단 줄 빼기, 섞인 줄은 번호만), 답 수치 대조(부호·소수점 무시, 기준 수치·단위 없는 수는 보지 않음).

- `RagApiTest`: 검색 경로(출처는 분석 완료 원문만, 근거 없음, `SOURCE_MISSING`, 빈 질문 400, AI 실패 502, 로그인만, 이미지 패널).
