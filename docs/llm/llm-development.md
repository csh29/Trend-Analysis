# llm-development.md — 공통 개발 규칙

**규범 문서** — 어떻게 작업해야 하는가. 모든 작업에 적용한다.
영역별 규칙은 [`backend/backend-development.md`](backend/backend-development.md)·[`ai/ai-development.md`](ai/ai-development.md)에, 기능별 규칙은 `features/` 문서에 있다.

## 1. 작업 순서

1. [`llm-analysis.md`](llm-analysis.md)로 전체를 보고, 고칠 영역(backend / ai) 문서와 기능 문서를 읽는다.
2. **이미 있는 것을 다시 만들지 않는다.** 공통 모듈·공통 처리(권한, fetch 래퍼, 그리드, 공통코드)가 있는지 먼저 확인한다.
3. 고친 뒤 해당 영역의 테스트를 통과시키고, 문서를 같이 고친다(아래 3절).

## 2. 환경

- 파이썬(`py`)·한글 경로(큰따옴표)·한국어(주석·로그·커밋) 규칙은 루트 [`CLAUDE.md`](../../CLAUDE.md)의 "항상 지키는 것"에 있다. AI 서비스 가상환경은 [`ai/ai-development.md`](ai/ai-development.md).

## 3. 주석·문서

- 주석은 "무엇"이 아니라 **"왜"**를 쓴다. 1~3줄로 쓰고, 주석에 다 못 쓰는 이유·함정은 기능 문서에 남긴다(작업 경위·과정은 남기지 않는다).
- 고친 곳에 맞는 문서를 같이 고친다.
  - 기능의 결정 사항·규칙·주의점이 바뀌면 → `features/<기능>.md`. **API·컬럼·파일 목록처럼 코드에서 읽을 수 있는 것은 적지 않는다** — 코드와 어긋나 틀린 문서가 된다. 이유가 있는 규칙, 사용자 결정, 겪은 함정만 남긴다.
  - 빌드·실행·구조·영역 공통 규칙이 바뀌면 → `backend/backend-development.md` 또는 `ai/ai-development.md`
  - 새 기능이면 `features/`에 문서를 만들고 루트 `CLAUDE.md` 문서 표와 `llm-analysis.md` 구현 현황 표에 넣는다.
  - 사람이 읽는 실행 방법·화면 목록이 바뀌면 `backend/README.md`도 고친다.
- 한 내용은 한 문서에만 쓰고 다른 문서는 링크한다.

## 4. 설계

- 아직 한 번뿐인 것을 미리 추상화하지 않는다(구현체 하나뿐인 인터페이스, "나중을 위한" 옵션).
- 분기가 여럿이라 단위 테스트가 필요한 판단 로직(해석·검증·집계 규칙 등)은 프레임워크 없이 테스트할 수 있는 순수 클래스·함수로 뺀다.
- 외부 호출 실패를 삼키지 않는다. "없음"과 "실패"를 구분할 수 있게 결과나 상태로 남긴다.

## 5. 시크릿

- `application*.properties`(backend)와 `ai/.env`는 `.gitignore`에 있다. 비밀번호·API 키를 커밋하지 않는다.
- 문서에는 설정 키 이름과 용도만 적는다. 키 값을 로그·응답·예외 메시지·문서에 넣지 않는다.

## 6. 작업 체크리스트

- [ ] 이미 있는 공통 모듈·공통 처리를 썼는가?
- [ ] backend를 고쳤으면 `./mvnw test`가 통과하는가? 새 API에 권한 테스트를 붙였는가([`auth-permission.md`](features/auth-permission.md) "확인할 것")?
- [ ] `ai/`를 고쳤으면 `ai/` 폴더에서 `.venv/Scripts/python -m unittest`가 통과하는가? 프롬프트를 고쳤으면 실제 호출로 확인했는가?
- [ ] 화면을 고쳤으면 브라우저에서 확인했는가?
- [ ] 바뀐 결정·규칙에 맞게 기능 문서·영역 문서를 고쳤는가? 실행 방법·화면 목록이 바뀌었으면 `backend/README.md`도?
